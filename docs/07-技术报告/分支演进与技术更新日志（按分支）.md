# BrainDance 分支演进与技术更新日志（按分支）

> 面向仓库分支与约 400+ 次有效开发提交的中文整理稿。写法偏 changelog，但重点不是罗列功能点，而是提炼每条分支体现出来的优化方向、工程方法、原创性改进和阶段性升级。

## 1. 说明与整理方法

本文档以 `main` 为对照基线，主要参考以下命令：

- `git log --reverse --no-merges main..branch`
- `git rev-list --count --no-merges main..branch`
- `git merge-base`
- `git cherry`

整理时遵循三条原则：

1. 优先写“相对 `main` 新增了什么”，避免把共享基线重复包装成多个分支的独立贡献。
2. merge commit 只在说明“分支继承关系、专题合流、集成节点”时使用，不把纯合并动作当成功能创新。
3. 重点关注三类内容：优化、工程方法、独创性改进。对纯同步分支或无独有 patch 的分支，单独说明，不注水。

## 2. 总体关系判断

从提交图谱和 `git cherry` 结果看，BrainDance 的分支大致可以分成四层：

### 2.1 技术源流层

- `origin/backend-dev`
- `origin/tianxingleo-da3`

这一层负责把 3DGS、AI 分割、WebGL、RAG、云任务这些能力从“能跑通的原型”推进为“具备工程方法的技术底座”。

### 2.2 主开发主线

- `origin/RatherHard-dev`
- `dev`

这两条线承载了最多的持续演进。前者更像“大一统开发主脉络”，后者则是最终更靠近当前主仓的主开发干线。

### 2.3 产品化与专题增强层

- `origin/raine_flutter`
- `tianxingleo`
- `origin/refactor/merge-page-files`
- `origin/tianxingleo-TimePeeling`
- `origin/tianxingleo-DoubleLine`
- `tianxingleo-flutter`

这一层更多体现产品交付、移动端体验、Viewer 交互、专题能力闭环和页面/工作流优化。

### 2.4 集成、验证与文档收束层

- `tianxingleo-doc`
- `tianxingleo-DLUT-L20`
- `origin/flutter_pr`

这一层并不都带来新的独有 patch，有些更多体现为文档工程、环境验证、合流与同步。

## 3. 关键分支详细日志

## 3.1 `origin/backend-dev`：后端原型与方法萌芽

### 分支定位

`origin/backend-dev` 是 BrainDance 最早期的 AI 后端试验支脉之一。它和当前 `main` 的历史存在明显分歧，但从提交内容看，已经能看到后续很多成熟方法的雏形：前处理质检、拍摄类型识别、降噪、尺寸裁剪、WebGL 对接和技术文档起盘。

### 阶段演进

#### 阶段一：后端训练原型起盘

- `6bedcbf` `first commit`
- `089dd9a` `修改gitignore，完成ai后端基础pytorch代码，实现高精度模型训练`

这说明项目的起点并不是单纯的前端应用，而是围绕 AI 后端、训练链路和实验可复现性展开。

#### 阶段二：打通训练结果到 Web 侧渲染

- `977d902` `实现坐标转换功能以提供给webgl`

这一提交的价值在于，它很早就把“生产 3D 数据”和“消费 3D 数据”连了起来。很多仓库会先做训练、最后再想展示，这里则在很早期就预留了 WebGL 渲染链路。

#### 阶段三：前处理质量治理成形

- `69f1675` `实现本地实现识别拍摄类型，实现降低噪声，自动裁剪模型大小`
- `06c77fc` `feat: 优化 3DGS 预处理流程，增强稳定性与清洗算法`

这一阶段最重要的不是新模型，而是方法意识：

- 拍摄类型识别，说明输入治理被显式拉到前面。
- 降噪和自动裁剪，说明目标是提升重建原料质量，而不是把坏数据硬塞进训练。
- 提交信息中已经体现出质量熔断、清洗策略升级、跨环境不稳定修补的意识。

#### 阶段四：从 README 到协作说明

- `4b83d55` `制作README，修改文档目录`
- `c9f7492` `refactor(ai_engine_demo):修改readme，ai_demo结构化`
- `394a18f` `docs: 更新README，增加项目概述和核心特性描述`
- `533dc1e` `feat: add detailed tech stack documentation and collaboration flow for 3D model processing system`

这表明该分支虽然早，但并不是“只顾实验不顾沉淀”。文档逐步从 README 说明，升级为技术栈和协作流程说明。

### 代表性优化点

- 很早就完成了训练结果到 WebGL 的坐标转换链路。
- 前处理阶段就引入拍摄类型识别、降噪、自动裁剪和清洗算法。
- 对低质量输入采取质检和熔断思路，而不是后置补救。

### 工程方法 / 架构手法

- 偏“研究工程”风格：代码、实验、文档同步推进。
- 强调输入数据治理，而不是只优化训练参数。
- 先打通闭环，再逐步结构化协作说明。

### 值得强调的升级与进步

这个分支代表项目从“想做 3DGS”迈入“知道哪些环节会失败、并开始建立方法论”的第一步。后续很多成熟能力，在这里都能看到原型。

### 分支定位

`origin/tianxingleo-da3` 是最强的技术源流分支之一，重点在 AI 引擎、3DGS 重建、分割管线、单图生成、RAG、WebGL Viewer 和云任务化。这条线不是小修小补，而是在持续重写“重建速度、分割质量、引擎结构和任务系统”。

这一阶段把重建质量的关键矛盾前移到了“输入质量控制”。这不是炫技，而是工程上最有效的降故障手段。

#### 阶段二：AI 分割从模型调用走向系统化优化

- `197e394` `引入llm，集成环境修正、AI背景涂黑与词汇树匹配`

- `d24daa4` `禁用 mask_path 注入以消除背景漂浮伪影`

这里最值得单独写的是几类原创性优化：

- 背景涂黑训练图生成
- 蒙版质量质检

- 文档建设与代码并行推进

5. **知识沉淀与协作能力显著增强**：README、开发文档、复现流程、比赛文档、技术报告和设计规则开始形成系统化知识库。
