# BrainDance 端侧模型微调全链路总结

> 整理自：`docs/04-本地问答与微调/`、`ai_engine/finetune_qwen3/` 下的 Part 0–33 实践记录及多份评测报告

---

## 1. 项目背景与目标

BrainDance（流光·记）是一个**空间记忆引擎**，将真实空间通过移动设备拍摄并重建为 3D 高斯泼溅（3DGS）模型，再通过自然语言问答检索和回忆这些空间。

端侧大模型微调的核心目标：

- **隐私保护**：所有问答在移动设备本地完成，不上传云端
- **极低幻觉**：模型必须"无充分证据则拒答，有证据则精准提取"
- **内存受限**：适配 OPPO 等手机的内存底座，模型需压缩到可部署体积
- **完整闭环**：从数据合成到量化部署的全工程流水线

---

## 2. 整体思路

```
Teacher（云端大模型）生成高质量训练数据
       ↓
Student（Qwen3-1.7B / 0.6B）通过 LoRA SFT 学习任务规范
       ↓
LoRA Adapter → Merge 为独立 HF 模型
       ↓
HF 模型 → GGUF 转换 → Q4_K_M / Q5_K_M 量化
       ↓
imatrix 重要性矩阵校准 → 最终端侧部署模型
       ↓
Flutter App 通过 llamadart 加载 GGUF 模型 + 本地 RAG 索引
```

核心思路可以概括为三个层次：

1. **工程链路优先** > 盲目增参数量 > 无工程裸跑
2. **任务化微调** 约束模型学会"证据驱动回答"而非"自由发挥"
3. **imatrix 量化** 在保持精度的同时压缩体积 60%+

## 3. 详细链路

### 3.1 Phase 1：环境准备

- 创建独立 conda 环境 `qwen3_ft`（Python 3.10），避免与项目运行环境 `Braindance` 交叉污染
- 安装 `torch 2.10.0+cu126`，配置 `CUDA_VISIBLE_DEVICES=1`（NVIDIA L20）
- 设置 `PYTHONNOUSERSITE=1`、`HF_ENDPOINT=https://hf-mirror.com`

### 3.2 Phase 2：训练数据构建

**数据来源**：

- 以 GPT-5.4 级 Teacher 模型生成高质量合成数据
- 覆盖 5 类场景：
  - `recent_hit`：近期命中的空间记忆
  - `must_answer`：必须回答的问题
  - `partial_coverage`：部分覆盖（仅部分对象有记录）
  - `stability`：稳定性测试
  - `no_hit`：无命中（模型应拒答）

**数据格式**：结构化为 evidence-driven QA 对，每条包含：

```json
{
  "messages": [
    {"role": "system", "content": "系统提示词，定义模型行为规范"},
    {"role": "user", "content": "问题 + 检索到的证据"},
    {"role": "assistant", "content": "参考回答"}
  ]
}
```

**迭代轮次**：

- Round 1–3：基础训练集构建与迭代
- Round 4：引入 `real_chain_failures` 作为失败案例定向补样
- Round 4.1：`partial_patch` 定向修复 partial_coverage 场景
- 后续：smoke 测试集 200 条 + 验证集 50 条

### 3.3 Phase 3：LoRA SFT 训练

**训练脚本**：`ai_engine/finetune_qwen3/scripts/train_lora_sft.py`

**LoRA 配置**：

| 参数 | 值 |
|---|---|
| rank (r) | 8 |
| alpha | 16 |
| dropout | 0.05 |
| target_modules | q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj |
| task_type | CAUSAL_LM |
| bias | none |

**训练超参**：

| 参数 | 值 |
|---|---|
| epochs | 2 |
| learning_rate | 2e-5（1.7B）/ 3e-5（0.6B） |
| batch_size | 1–2 per device |
| gradient_accumulation_steps | 8 |
| warmup_ratio | 0.05 |
| optimizer | adamw_torch |
| lr_scheduler | cosine |
| weight_decay | 0.01 |
| max_grad_norm | 1.0 |
| precision | bf16（自动降级 fp16/fp32） |
| cutoff_len | 1536–2048 |

**关键技术细节**：

- **Assistant-only loss masking**：只对 assistant 回复部分计算 loss，prompt 部分置为 -100
- **Gradient checkpointing**：节省显存
- **Qwen3 chat template**：关闭 thinking mode（`enable_thinking=False`）
- **可训练参数占比**：0.6B 约 0.84%，1.7B 约 0.5%

**基座模型对比**：

| 基座 | 总参数 | 可训练参数 | 可训练占比 |
|---|---|---|---|
| Qwen3-0.6B | 601M | 5.0M | 0.84% |
| Qwen3-1.7B | ~1.7B | ~8.5M | ~0.5% |

### 3.4 Phase 4：LoRA Merge

**脚本**：`ai_engine/finetune_qwen3/scripts/merge_lora_adapter.py`

```bash
python merge_lora_adapter.py \
  --base_model Qwen/Qwen3-1.7B \
  --adapter_path outputs/qwen3_1p7b_lora_sft_round4_1_patch_mixed \
  --output_dir releases/qwen3_1p7b_braindance_round4_1_patch_mixed_merged
```

- 通过 PEFT 的 `merge_and_unload()` 将 LoRA 权重合并进基座
- 输出独立 HuggingFace 模型目录（含 tokenizer）
- 生成 `merge_metadata.json` 记录合并配置

### 3.5 Phase 5：GGUF 转换与量化

**脚本**：`ai_engine/finetune_qwen3/scripts/prepare_quantization_artifacts.py`

**流程**：

1. HF → GGUF（f16 精度）：`convert_hf_to_gguf.py`
2. f16 GGUF → 量化 GGUF：`llama-quantize`

**量化方案对比**：

| 量化版本 | 体积（约） | strict 综合分 | 特点 |
|---|---|---|---|
| 1.7B merged（未量化） | ~3.3GB | 96.67 | 质量基线 |
| Q4_K_M | ~1.0GB | 94.21 | 正确性可接受，体验侧弱 |
| Q5_K_M | ~1.2GB | 88.38 | strict 集退化（partial_negation 回退） |
| Q5_K_M + imatrix | ~1.2GB | **94.21** | 修复 strict 回退，当前部署主线 |

### 3.6 Phase 6：Importance Matrix（imatrix）校准

**问题**：Q5_K_M 在 strict 无泄漏集上 `partial_missing_negation` 从 0.0556 退化到 0.4444。

**方案**：

- 校准语料：benchmark + strict benchmark + sft_train，共 256 条
- 工具：`llama-imatrix`，128 chunks
- 产物：`imatrix_chat_256_chunks128.gguf`

**关键发现**：

- imatrix 对 Q5 有效：`partial_missing_negation` 0.4444 → 0.0556，基本修复
- imatrix 对 Q4 无效甚至有害：综合分从 94.21 降到 91.20
- 最终结论：**Q5_K_M + imatrix** 是最优量化方案

### 3.7 Phase 7：端侧部署

**Flutter 集成**：

- 加载引擎：`llamadart`（Flutter llama.cpp 绑定）
- 模型格式：GGUF
- 本地 RAG：SQLite 向量数据库
- 默认文件名：`qwen3-1.7b.gguf`

**路由策略**（`docs/query_routing_strategy.md`）：

| query_class | retrieval_route | answer_route | 说明 |
|---|---|---|---|
| greeting | non_retrieval | fixed_response | 直接固定回复 |
| persona | non_retrieval | fixed_response | 直接固定回复 |
| inventory | inventory_special_case | inventory_formatter | 资产盘点走专门查询 |
| recent_capture | recent_list / vector_only | lora_generation | 时间问法优先 recent list |
| object_lookup | vector_only / lexical_fallback | lora_generation | 实体检索交给模型 |
| partial_coverage | vector_plus_filter | lora_generation | partial 依赖 support map |

**多重防幻觉保险**：

1. Intent Formatter：统一查询格式
2. Evidence-driven Generation：只基于检索证据回答
3. Literal Fallback：兜底机制

## 4. 模型矩阵与效果

### 4.1 所有本地候选版本

| 版本 | 方法 | 体积 | 角色 |
|---|---|---|---|
| 1.7B LoRA | LoRA SFT | adapter ~20MB + 基座 3.3GB | 严格集质量上界 |
| 1.7B merged | LoRA → merge | ~3.3GB | 质量基线对照 |
| 1.7B Q5_K_M + imatrix | merge → GGUF → Q5 → imatrix | **~1.2GB** | **当前部署主线** |
| 1.7B Q4_K_M | merge → GGUF → Q4 | ~1.0GB | 不推荐（imatrix 对 Q4 无效） |
| 0.6B LoRA | LoRA SFT | adapter ~10MB + 基座 1.2GB | 备用轻量方案 |
| 0.6B full SFT | 全参 SFT | ~1.2GB | 实验支线（风格更好但纪律略弱） |

### 4.3 与云端模型对标（严格集）

| 模型 | 综合分 |
|---|---:|
| **Local LoRA 1.7B** | **98.89** |
| Cloud qwen2.5-32b (opt) | 97.54 |
| Cloud qwen3-32b (opt) | 92.62 |
| Cloud qwen3-8b (opt) | 90.25 |
| Cloud qwen-turbo (opt) | 86.32 |
| Local Base 1.7B | 76.65 |
| Cloud qwen3-8b (no-opt) | 62.05 |
| Cloud qwen3-32b (no-opt) | 62.04 |

**核心结论**：1.7B LoRA 在严格集上超越所有云端模型（包括 32B），证明"工程链路 + 任务化微调"远比"盲目增大参数"有效。

### 4.4 四象限消融实验

同一 Qwen3-1.7B 基座，"微调前后 × 有无工程优化"：

| 组合 | 综合分 |
|---|---:|
| Base + NoOpt | 54.59 |
| Base + Opt | 76.65 |
| LoRA + NoOpt | 57.03 |
| **LoRA + Opt** | **98.89** |

结论：工程优化贡献 +22 分，LoRA 微调贡献 +42 分，叠加效果最强。

### 4.5 部署小样本真实调用链（Part 29）

| 候选 | 平均 retrieval(ms) | 平均 generation(ms) | 平均 TTFT(ms) | 平均总时长(ms) | 平均峰值显存(MB) |
|---|---:|---:|---:|---:|---:|
| 0.6B LoRA | 8217 | 320 | 68 | 8536 | 1637 |
| 1.7B merged | 8229 | 210 | 28 | 8439 | 3866 |
| **1.7B Q5+imatrix** | 7461 | 1030 | 829 | 8492 | **794** |

- 总时长三者接近（~8.5s），主要被 retrieval 吃掉
- Q5+imatrix 显存最低（794MB），但 TTFT 最慢（829ms）
- 1.7B merged 生成最快（210ms），但显存最高（3866MB）

### 4.6 新增未见数据 OOD 泛化（frozen 口径）

| 模型 | 端到端通过率 | retrieval 正确时通过率 |
|---|---:|---:|
| 1.7B LoRA | 0.5556 | 0.8333 |
| 0.6B LoRA | 0.3889 | 0.5833 |
| **1.7B Q5_K_M + imatrix** | **0.6111** | **0.9167** |

Q5+imatrix 在未见过的新数据上甚至略微领先 LoRA。

## 5. 最终部署决策

### 当前部署主线

**1.7B Q5_K_M + imatrix GGUF**（~1.2GB）

- Flutter Recall 本地 AI 入口已是 `GGUF + llamadart`，工程接入最顺
- strict 集核心任务指标已追平 Q4_K_M
- 资源占用最低（显存 794MB）
- 新增 OOD 数据上表现最好

### 备用方案

**0.6B LoRA**

- 体量更小，适合极致轻量端侧
- strict 集表现比预期更稳（综合分 97.54）
- 尚需 GGUF 量化路径才能直接接入 Flutter

### 质量基线

**1.7B merged**

- 综合分 96.67，所有端侧版本的质量对照上界
- 显存占用过高（3866MB），不适合直接部署

---

## 6. 关键经验与教训

1. **工程链路 > 任务化微调 > 参数量**：1.7B LoRA + Opt 超越 32B 云端模型
2. **imatrix 对 Q5 有效、对 Q4 有害**：不能假设量化校准普遍有效
3. **严格无泄漏评测是必须的**：原始 benchmark 会虚高，strict 集才能暴露真实退化
4. **部署决策要基于真实调用链**：不是学术分数最高的版本最合适，而是工程接入最顺 + 资源约束内质量最优的版本
5. **训练数据迭代采用定向补样**：从真实失败案例中提取补丁数据，而非盲目扩充
6. **assistant-only loss masking**：对对话场景微调至关重要，避免模型学习 prompt 部分
