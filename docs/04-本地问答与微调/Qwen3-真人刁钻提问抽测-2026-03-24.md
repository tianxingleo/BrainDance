## 二、整体观察

### 1. 当前主线 `1.7B LoRA` 的优点

- 最核心优点依旧成立：**不乱编**
- 在这 15 题里，没有出现明显的外部知识幻觉
- 大多数超域问题都能收敛为“暂无相关记录 / 没有相关信息”
- 比 `0.6B` 更能守住时间问题，不容易把历史约束直接冲成“最近模型总结”

### 2. 当前主线 `1.7B LoRA` 的主要短板

- **高阶意图缺口明显**
  - “时间线”
  - “去过哪些地方”
  - “用户喜好分析”
  - “重复内容检测”
  - “房间大小估算”
- 这些题并不是单纯 `no_hit`，而是需要：
  - 聚合多条证据
  - 做统计 / 去重 / 时间排序
  - 从对象层提升到“地点 / 偏好 / 场景属性”层
- 当前链路对这类题缺乏专门 formatter，最后容易退回成泛化 summary 或直接拒答

### 3. `0.6B LoRA` 的额外风险

- `0.6B` 在这组题上更容易**误路由**
- 最典型的是：
  - “三个月前的模型出现最多的物体是什么”
  - 被直接答成“最近生成过3个模型……”
- 说明更小模型在 `inventory / time_qa / recent_capture` 三者边界上更脆

## 三、问题归类

### A. 安全拒答基本达标

这类问题当前表现是合格的：

- 你的家里几口人
- 你在哪里上班
- 你住在哪里
- 服务器是什么时候开始运行的
- 为我介绍《原神》  
  在当前“只基于本地记忆证据作答”的设定下，拒答比胡说更对
- 你喜欢吃什么
- 我所在地最有名的景点是什么

### B. 没有乱答，但能力缺口明显

- 你的参数量和预训练数据是什么
- 近期拍过的照片有没有重复内容
- 估算最新模型中的房间大小
- 请根据拍摄内容分析用户喜好
- 国庆放假期间我创建了多少模型

这些题本质不是简单 `object_lookup`，需要：

- 静态系统信息
- 跨样本去重
- 时段计数
- 聚合分析
- 几何元数据

### C. 当前最需要优先修的 route failure

- 三个月前的模型出现最多的物体是什么
  - `0.6B` 已经明显答偏
- 请将所有模型的拍摄时间梳理为一条时间线
  - 两个模型都没有输出 timeline
- 我去过哪些地方
  - 两个模型都答成了“最近拍到什么物体”

这三类问题最危险，因为它们会让用户感觉“模型听懂了句子，但答错了任务”。

## 四、优化方向

### 1. 增加 OOD / 能力边界专用路由

建议在当前 `query_class` 之外，补一个更上游的能力判定层，把问题先分成：

- `personal_profile`
- `model_self_info`
- `ops_runtime`
- `external_world_knowledge`
- `memory_retrieval`
- `memory_aggregation`

这样可以把：

- “你的参数量和预训练数据是什么”
- “服务器是什么时候开始运行的”
- “为我介绍《原神》”

从普通检索链路里提前分流，避免统一落成 `object_lookup -> no_hit`。

### 2. 为高阶问题补专用 formatter，而不是继续依赖泛化生成

优先级最高的 formatter 建议是：

1. `timeline_formatter`
   - 输入：inventory hits
   - 输出：按时间排序的模型列表
2. `place_summary_formatter`
   - 输入：scene 描述 / tag / location hint
   - 输出：用户去过的地点或场景类别
3. `preference_summary_formatter`
   - 输入：跨场景对象分布
   - 输出：保守版用户兴趣总结
4. `duplicate_detection_formatter`
   - 输入：近时间 + 高相似描述 / 同源 2D+3D 记录
   - 输出：是否存在重复内容

### 3. 强化意图路由训练数据

这次暴露出当前训练集对以下问法覆盖不足：

- “我去过哪些地方”
- “梳理为一条时间线”
- “三个月前……出现最多的物体”
- “根据拍摄内容分析用户喜好”

建议新增一批 hard cases，明确标注：

- 正确 `query_class`
- 应走的 formatter
- 在证据不足时的标准拒答口径

### 4. 给“模型自我信息”挂静态知识回答

像“参数量 / 基座模型 / 预训练数据”这种问题，其实不必走记忆检索。

建议直接挂一个静态 metadata：

- 当前模型名
- 参数量
- 微调方式
- 是否基于公开基座
- 是否能回答预训练数据细节

这样至少能把：

- “你的参数量和预训练数据是什么”

从“暂无相关记录”升级成更像产品助手的稳定回答。

### 5. 把这 15 题纳入固定人工回归集

建议直接把这组题沉淀成一个小型 regression case：

- 每次 route 调整后都跑
- 不只看 benchmark 指标
- 专门盯：
  - 是否乱编
  - 是否误路由
  - 是否把“地点 / 时间线 / 偏好”答成“物体摘要”

---

## 五、本轮结论

一句话总结：

> 当前 `1.7B LoRA` 主线在“安全拒答、不乱编”上依旧明显优于更小模型，但在“时间线 / 地点 / 偏好 / 去重 / 统计”这类高阶问题上仍然缺少专门能力层；`0.6B` 则在这些问题上更容易直接误路由。

更具体一点：

- 如果目标是“先别胡说”，当前主线已经基本合格
- 如果目标是“像真正的本地记忆助手一样理解时间线、地点和用户偏好”，当前系统还需要补：
  - 上游能力分流
  - 聚合型 formatter
  - hard case 路由训练集
