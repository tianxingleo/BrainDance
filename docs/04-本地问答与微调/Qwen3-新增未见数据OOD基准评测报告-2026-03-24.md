# Qwen3 新增未见数据 OOD 基准评测报告（2026-03-24）

## 1. 目标

这轮评测不再复用之前那批约 `20` 个老样本的变体，而是直接基于 **Supabase 里训练后新增的真实数据**，构造一套新的 OOD benchmark，回答两个问题：

1. 当前本地问答链路对“模型没见过的新 scene / 新 object / 新 tag”到底能不能泛化。
2. 真正拖后腿的是模型生成，还是 retrieval / route / formatter 本身。

## 5. 总结论

### 5.1 retrieval 才是这轮最大的瓶颈

可计分 `18` 题里：

- `retrieval_ok_rate = 0.6111`
- 也就是只有 `11 / 18` 题真正把预期证据捞上来了
- 被 retrieval 直接卡死的有 `7 / 18`

按组看：

| 组别 | 题数 | retrieval_ok_rate |
| --- | ---: | ---: |
| must_answer | 8 | 0.3750 |
| no_hit | 4 | 0.5000 |
| partial_coverage | 6 | 1.0000 |

这说明当前链路最不稳的不是 partial，而是：

- 新对象命中
- “最近”类题目
- 新增数据持续流入时的 `recent_list` 稳定性

### 5.2 一旦 retrieval 正确，`1.7B LoRA` 和 `Q5+imatrix` 基本打平

| 候选 | 端到端通过率 | retrieval 正确时回答通过率 | partial_coverage 通过率 |
| --- | ---: | ---: | ---: |
| 1.7B LoRA | **0.5000** | **0.8182** | **0.6667** |
| 0.6B LoRA | 0.3333 | 0.5455 | 0.1667 |
| 1.7B Q5_K_M + imatrix | **0.5000** | **0.8182** | **0.6667** |

这轮最关键的判断是：

1. `0.6B LoRA` 在未见数据上的 **partial reasoning 明显更脆**。
2. `1.7B LoRA` 和 `1.7B Q5_K_M + imatrix` 在这套 OOD 小基准上，质量已经非常接近。
3. 端到端分数没有继续拉开的核心原因不是模型，而是 retrieval 先挡掉了太多题。

### 5.3 当前 benchmark 里有一半题已经不是“纯模型题”

- `formatter_case_count = 12`
- `model_generated_case_count = 12`

也就是说，这轮 24 题里已经有一半会落到 formatter / special route。
因此如果只看最后答案，不拆链路，很容易误判成“模型变强/变弱”。

## 6. retrieval 暴露出的真实问题

本轮被 retrieval 阻塞的 7 个 scoreable case 里，最典型的是：

1. `最近有珍珠奶茶吗？`
   预期应该命中新桌面奶茶样本，但实际被更晚插入的 `recent_list` 内容顶掉。
2. `最近有手冲咖啡场景吗？`
   当前链路把它跑成了 `time_qa + no_hit`。
3. `最近有曲奇饼干吗？`
   被更新后的“最近插画”样本劫持，没落到真实食品静物。
4. `最近拍到过猫咪吗？`
   数据库对象是 `橘白猫`，用户自然问法是 `猫咪`，当前链路没成功泛化。
5. `最近拍到过斑马涂鸦吗？`
   新涂鸦场景存在，但 `斑马涂鸦` 这类复合表述仍没稳定命中。
6. `最近拍到过打印机吗？`
   当前库里 actually 命中了 `白色打印机与文具盒`，所以这题暴露的是我原先 benchmark 设定已经被新库打脸了。
7. `最近有咖啡机吗？`
   被 recent route 误带成泛化“最近拍到什么”，没有给出安全拒答。

这里最重要的信号不是某一道题本身，而是：

- 新对象 lexical alias 不稳
- `recent_list` 极易被“更晚插入但无关”的样本挤占
- benchmark 如果不锁数据库快照，结果会随着远端持续增量而漂移

---

## 7. 模型差异：真正拉开的是 partial_coverage

### 7.1 `1.7B LoRA / Q5+imatrix` 的优势

它们都能稳定通过这些新分布 partial 题：

- `珍珠奶茶 + 机械键盘 / 咖啡机`
- `猫咪 + 风扇 / 微波炉`
- `斑马 + 番茄 / 长颈鹿`
- `手冲咖啡 + 玻璃滤杯 / 咖啡机`

典型正确口径是：

- 命中部分明确说有
- 未命中部分明确否定
- 不把“咖啡相关”泛化成“咖啡机也有”

### 7.2 `0.6B LoRA` 的主要短板

`0.6B` 主要败在 partial：

- 漏报已命中对象
- 把已命中对象答成未命中
- 对新 object 的局部组合保持不住

最明显的例子：

- `珍珠奶茶 + 机械键盘 / 咖啡机`
  - `0.6B` 漏掉了 `机械键盘`
- `手冲咖啡 + 玻璃滤杯 / 咖啡机`
  - `0.6B` 把 `玻璃滤杯` 答成未命中
- `斑马 + 番茄 / 长颈鹿`
  - `0.6B` 直接把支持关系答反

所以这一轮可以非常明确地说：

- `0.6B` 还能做轻量备用
- 但如果问法升级到“新数据 + partial negation + 复合对象”，它和 `1.7B` 已经不是一个级别

---

## 8. 探索题观察

探索题的价值不是打分，而是看 route failure。

### 8.1 有所进展的

- `最近有没有明显 AI 生成感或者合成感很强的图像？`
  - 当前能拉到 `巨型机械钟 + 悬浮表演者` 这类明显目标
- `最近这些新模型里，有哪些更像食品或零食静物？`
  - 当前能命中 `曲奇饼干堆 + 黑巧克力 + 包装糖`

### 8.2 仍然明显答偏的

- `请把最近新增的模型按时间倒序梳理一下。`
  - 还是被压扁成“最近生成过 3 个模型”
  - 没有真正输出 timeline
- `我最近去过哪些地方？`
  - 仍然被 recent route 答成“最近拍到什么物体”
- `近期拍过的照片里有没有重复内容？`
  - 还是统一拒答，没有去重能力
- `请根据最近新增模型的拍摄内容分析一下用户偏好。`
  - 仍然退化成 inventory summary

这说明：

1. `timeline / place_summary / preference_summary / duplicate_detection`
   这些 formatter 依然是空白区
2. 这部分不是继续补 SFT 变体就能自然长出来的
3. 更像是必须补路由层和专用 formatter

## 9. 这轮 benchmark 的最终判断

### 9.1 关于泛化

如果问题是：

> 这些微调模型在你新加的、训练没见过的数据上还有没有泛化能力？

当前最准确的答案是：

- **有，但只在 retrieval 先对的前提下。**

更细一点说：

- `1.7B LoRA / 1.7B Q5_K_M + imatrix`
  在 retrieval 正确时，已经能在不少未见 object 组合上保持不错的 partial 纪律
- `0.6B LoRA`
  在简单 hit / no-hit 上还行，但复合 partial 明显扛不住

### 9.2 关于主线选择

这轮结果没有推翻之前的主线判断，反而更强化了它：

- 部署主线：`1.7B Q5_K_M + imatrix`
- 研发质量基线：`1.7B LoRA`
- 轻量备用：`0.6B LoRA`

因为：

- `Q5+imatrix` 这轮质量没有比 `1.7B LoRA` 更差
- 真正限制端到端效果的主要是 retrieval，不是它的生成退化
- `0.6B` 则已经在 OOD partial 上显著掉队

---

## 10. 本轮已定位的工程瓶颈

这轮不是只得到了一张分数表，更重要的是把瓶颈拆清楚了：

1. benchmark 漂移问题已经通过 snapshot 固化得到解决，不再是“结果不可复现”的状态。
2. retrieval alias / lexical 扩展仍然是最主要的端到端短板。
3. `recent_list` 对“最新但无关样本”的敏感性，是 must_answer / recent_hit 类题最容易失真的来源。
4. `timeline / place_summary / preference_summary / duplicate_detection` 仍然主要是 formatter 能力空白，不是简单继续补 SFT 就会自然长出来。
5. 如果只看模型层面，真正最值得关注的泛化差距仍然是 `partial_coverage on unseen objects`。

## 12. 二期高难方向：空间关系题

你提的这类题非常关键，因为它们比当前 benchmark 再高一层：

- `A 是不是在 B 的左边 / 右边 / 前面`
- `A 和 B 离得近不近`
- `A 更靠近 B 还是 C`
- `A / B / C 三者的相对位置关系`

这类题我已经单独落成了一个二期 hardcase 文件：

- `ai_engine/finetune_qwen3/data/braindance_qwen3_unseen_ood_spatial_hardcases_20260324.json`
  本地评测数据文件，不纳入 Git。

当前先不把它们并入主计分集，原因不是不重要，而是：

1. 当前链路主干仍是“scene-level retrieval + text formatter”
2. `memory_poses` 虽然有 `transform_matrix`，但现在还没有 object-level grounding
3. 也就是说，系统能找到“这张图”，但还不能稳定知道“图里这个物体的精确 2D/3D 位置”

所以这类题更像下一阶段的专用评测轴，而不是现阶段和 `object_lookup / partial_coverage` 混在一起的通用分数。

### 11.1 这批空间题为什么更难

和当前 benchmark 相比，它们至少多了一层：

- 不只是“有没有这个物体”
- 而是要先锁定多个物体实例
- 再估计它们在同一视角里的相对方位
- 有些题还需要估计深度、距离或三元关系

例如：

- `猫在风扇左边还是右边`
- `奶茶杯更靠近键盘还是笔记本`
- `玻璃分享壶、滤杯、注水壶从左到右是什么顺序`
- `猫、风扇、冰箱谁位于另外两个之间`

这些题如果只靠当前文字描述检索，大概率会出现：

- route 直接退成普通 object lookup
- retrieval 命中 scene，但 answer 不会关系推理
- 或者模型胡乱根据常识补位置

### 11.2 当前最适合先做的 spatial 子任务

不建议一开始就上开放式三元关系，可以按下面顺序推进：

1. `left_right_binary`
   - A 在 B 左边还是右边
2. `distance_bucket`
   - A 和 B 离得近 / 中 / 远
3. `distance_comparison`
   - A 更靠近 B 还是 C
4. `triple_ordering`
   - A/B/C 从左到右顺序
5. `between_relation`
   - 三者中谁位于另外两个之间

### 11.3 如果要真正跑起来，链路上还缺什么

至少还缺三样东西：

1. `object grounding`
   - 从 scene/frame 中定位对象实例，而不只是命中 scene 描述
2. `spatial formatter`
   - 把多个对象的位置关系整理成稳定短答
3. `spatial benchmark metadata`
   - 每题要带标注好的 object pair / triplet / relation type / 预期答案

所以更准确地说：

- 现在的系统已经能测“新对象有没有被识别和守纪律回答”
- 下一阶段要测的，就是“识别到以后能不能做空间推理”
