## 二、先用外行也能懂的话说清楚：他们到底在做什么

这条线做的不是“把一个聊天机器人训得更会聊天”，而是：

- 让一个体积较小、未来可以在本地设备运行的模型
- 学会根据 BrainDance 自己的检索结果来回答问题
- 有证据时稳定回答
- 没证据时明确拒答
- 尽量不乱编
- 最终还能压缩到适合移动端部署的体积

换句话说，这不是传统意义上的“开放世界百科问答模型训练”，而是 **面向私有空间记忆检索场景** 的定向微调和部署工程。

这件事之所以重要，是因为 BrainDance 的目标不是让模型回答“世界上最高的山是什么”，而是回答类似：

- 我最近拍过什么？
- 最近有奶茶相关的场景吗？
- 有没有地球仪相关的画面？
- 哪些模型里出现过某个物体？

这类问题的关键不在于模型“知道多少常识”，而在于模型能不能：

- 正确利用检索到的证据
- 不把没检索到的东西编出来
- 把部分命中和完全命中区分清楚
- 用比较自然、像产品的句子回答

因此，这条主线实际上是一个 **“检索 + 路由 + 格式化回答 + 小模型微调 + 量化部署”** 的组合工程，而不是单一训练任务。

## 四、这条线最早的目标是什么

根据 [Qwen3-1.7B-微调实践记录.md](/ltx-data/BrainDance/docs/04-本地问答与微调/Qwen3-1.7B-微调实践记录.md) 和 [本地问答微调文档补充说明.md](/ltx-data/BrainDance/docs/04-本地问答与微调/本地问答微调文档补充说明.md)，最早的目标不是“记住更多用户事实”，而是训练模型学会一种行为模式：

1. 有命中时稳定回答。
2. 无命中时安全拒答。
3. 面对部分命中时，能说清“哪些有、哪些没有”。
4. 回答风格尽量短、自然、像产品输出，而不是机械模板。

这意味着训练对象不是一个自由聊天代理，而是一个 **“基于检索证据回答的本地问答引擎”**。

这个目标判断非常关键，因为它决定了后面所有评测标准都偏向：

- 幻觉控制
- 否定表达完整性
- partial coverage 纪律性
- must-answer 聚焦能力
- 证据利用率

而不是：

- 开放域知识量
- 文采
- 长链推理
- 一般闲聊能力

## 五、最早期阶段做了哪些基础工作

这一阶段主要记录在总实践文档的 Part 0 到 Part 15 中。

### 1. 环境没有直接复用，而是单独隔离

最开始，团队先检查了项目原有的 `Braindance` conda 环境，结论是：

- 该环境存在用户级 Python 包污染。
- 训练所需的关键依赖不完整。
- 如果继续在原环境上修补，风险较高，也不利于排障。

因此他们没有在原环境上硬凑，而是新建了独立训练环境：

- `conda create -n qwen3_ft python=3.10`

这一步说明这条线从一开始就重视环境稳定性，而不是“先跑起来再说”。

### 2. 训练软件栈做过一次路线调整

最初计划是：

- `LLaMA-Factory + Qwen3-1.7B + LoRA SFT`

但由于：

- 最新版 `LLaMA-Factory` 要求 Python 3.11
- 当前已装好 CUDA PyTorch 的环境是 Python 3.10

团队最终改成：

- `transformers`
- `peft`
- `trl`
- `accelerate`
- 自写最小 LoRA SFT 训练脚本

这说明项目选择的是“最快形成闭环”的路线，而不是最依赖外部框架的路线。

### 3. 第一版数据集和训练脚本很早就落地

在早期阶段已经完成：

- 数据集构建脚本 `build_sft_dataset.py`
- LoRA 训练脚本 `train_lora_sft.py`
- smoke 评测脚本 `run_smoke_eval.py`

训练样本的组织不是纯自然语言，而是带结构化检索结果的对话格式，核心字段包括：

- `question`
- `retrieval.intent`
- `retrieval.hit_count`
- `retrieval.evidence`

这说明团队从一开始就在训练模型“看懂证据并按证据回答”，而不是只训练普通问答。

### 4. 先做最小可运行数据，再扩轮次

第一版数据量并不大，目标不是一开始就训出最强模型，而是先验证几个基础问题：

- GPU 能不能稳定跑。
- 模型能不能正确读入结构化证据。
- 训练脚本是不是可用。
- 输出行为是否朝“少乱答、按证据说话”方向收敛。

这是一种比较稳健的工程推进方式。

### 5. 很早就意识到“不是单靠加训练就能解决一切”

随着实验推进，文档里越来越多地出现以下判断：

- 继续开新 LoRA 不一定是最高优先级。
- 真实链路的问题不全在模型。
- 某些问题更像 retrieval / route / formatter 问题。

这为后续 Part 16 之后的“链路观测和调优”埋下了基础。

这是整条主线里最值得重视的转折期。

### 1. Part 16：先补可观测性，而不是继续盲训

团队在 Part 16 里做了非常关键的工程动作：

- 给真实链路补 `query_class`
- 补 `retrieval_route`
- 补 `answer_route`
- 给 interactive debug 日志补人工反馈标签
- 新增路由聚合脚本
- 明确 query routing strategy

这意味着后续团队不再只能说“这个回答看起来不对”，而是能更精确地回答：

- 是问题分类错了？
- 是检索没捞到？
- 是 fallback 兜底路径走错了？
- 还是 formatter 没接住？
- 或者真的是 LoRA 生成不稳定？

这一步的价值非常大，因为它让优化依据从主观感觉转成了可统计的链路信息。

### 2. Part 17：专项优化 object_lookup

在有了观测能力之后，团队发现当前的主要矛盾不再是“模型不会回答”，而是：

- 某些 `object_lookup` 问法召回不稳
- 某些 query 过度依赖 lexical fallback
- 有些问题更适合走确定性 formatter，而不是让模型自由生成

换成人话说，就是：

“模型大致守规矩了，但‘找东西’这件事还不够稳。”

于是 Part 17 做的是专项检索优化，而不是简单开新一轮 LoRA。

### 3. Part 18：体验层和 formatter 打磨

Part 18 的重点是把回答做得更像产品，而不是更像调试输出：

- recent formatter 改成固定短答风格
- must-answer formatter 改成主目标优先
- inventory formatter 改成更自然的人话
- abstract semantic query 增加显式兜底

这一步很重要，因为它说明团队已经开始区分：

- 哪些问题需要模型生成
- 哪些问题更适合规则化输出

这种区分对低幻觉产品来说非常关键。

### 4. Part 19：最小可用本地问答 CLI 落地

Part 19 新增了：

- [local_qa_cli.py](/ltx-data/BrainDance/ai_engine/finetune_qwen3/scripts/local_qa_cli.py)

这件事的意义在于：

- 本地问答能力有了统一入口。
- 不再只能靠实验脚本逐个调试。
- 真实手测回归问题也能更快暴露。

同时，这个 CLI 还带动了测试和回归修复，例如：

- [test_local_qa_cli.py](/ltx-data/BrainDance/tests/test_local_qa_cli.py)
- [test_part20_local_qa_regressions.py](/ltx-data/BrainDance/tests/test_part20_local_qa_regressions.py)

### 2. Part 21：Qwen3-0.6B LoRA 首轮训练

这一支线解决的是“有没有更轻量的备选方案”。

结论不是 0.6B 失败，而是：

- 0.6B 可以作为轻量路线保留
- 但还不足以替代 1.7B 主线

### 3. Part 22：1.7B LoRA merge 和 GGUF 转换

这一部分把 1.7B LoRA 合并成独立模型，并真实做了 GGUF 转换和量化。

这一步的意义很实际：

- 没有 merge，部署时仍依赖 base model + adapter 的组合
- 有了 merge 和 GGUF，才真正进入“本地运行、移动端接入”的语境

### 4. Part 23 到 Part 27：量化版本不只是做出来，还做了对比和归因

团队没有停在“量化成功”这一步，而是继续比较：

- `Q4_K_M`
- `Q5_K_M`
- 原始 benchmark
- strict benchmark

然后发现：

- `Q5` 在原始 benchmark 上看起来比 `Q4` 好
- 但在 strict 集上却出现回退

这就引出了 Part 27 的核心问题：

- 为什么 `Q5` 在 strict 集上退化？

文档的结论是：

- `Q5` 更倾向于自然、聚焦命中对象
- 但对“未命中对象要明确否定”这一 strict 规则遵守得更差

这不是简单的“模型坏了”，而是回答风格偏移导致的行为退化。

### 5. Part 28：importance matrix 量化成为关键转折

Part 28 是整条部署线里非常关键的一步。

团队新增：

- `export_imatrix_corpus.py`
- `run_imatrix_quantization_gpu1.sh`

并做了：

- 基于 benchmark + strict benchmark + train 数据导出校准语料
- 用 `imatrix` 做 `Q4` 和 `Q5` 的量化复测

得出的核心结论是：

- `Q5_K_M + imatrix` 在原始集和 strict 集都显著优于原始 `Q5`
- `Q5 + imatrix` 把 strict 集上的关键回退基本修回来了
- `Q4 + imatrix` 不但没明显更好，甚至可能退步

这意味着：

- `imatrix` 不是“对所有量化都有效”
- 但它对 `Q5` 这条主线非常关键

### 6. Part 29：部署候选正式定型

Part 29 最重要的不是实验细节，而是决策已经明确写出来了：

- 当前部署主线：`1.7B Q5_K_M + imatrix GGUF`
- 备用方案：`0.6B LoRA`
- 质量基线候选：`1.7B merged`

团队给出的理由也很清楚：

- Flutter 当前本地 AI 入口是 `GGUF + llamadart`
- `Q5 + imatrix` 已经验证过 strict 稳定性
- 资源占用更适合真实部署
- 从“今天就继续往产品里接”的角度最顺

这说明到了 Part 29，这条线已经不是“研究哪个版本更强”，而是“明确产品应该优先接哪个版本”。

## 八、0.6B 全量微调支线：做了什么、结论如何

这一部分单独对应：

- [Qwen3-0.6B-微调实践记录-Part31.md](/ltx-data/BrainDance/docs/04-本地问答与微调/Qwen3-0.6B-微调实践记录-Part31.md)
- [Qwen3-0.6B-微调实践记录-Part32.md](/ltx-data/BrainDance/docs/04-本地问答与微调/Qwen3-0.6B-微调实践记录-Part32.md)
- [Qwen3-0.6B-微调实践记录-Part33.md](/ltx-data/BrainDance/docs/04-本地问答与微调/Qwen3-0.6B-微调实践记录-Part33.md)

这条支线的核心问题是：

- 既然 0.6B 更小，能不能通过 full SFT 把它训练到又自然又可靠，从而替代 0.6B LoRA？

### 1. Part 31：0.6B full SFT 首轮可行性

首轮结论比较克制：

- `0.6B full` 确实已经真实跑通
- 训练、smoke eval、原始 benchmark、strict benchmark 都可复现
- 它的优势主要体现在：
  - `natural_style`
  - `must_answer_focus`
  - 某些场景下的表达自然度

但问题也很清楚：

- 它没有稳定打赢 `0.6B LoRA`
- 在某些 partial coverage 场景下仍有 unsupported leakage 风险

### 2. Part 32：保守学习率实验

团队又试了：

- `1e-5`
- `8e-6`
- `5e-6`

结论是：

- `1e-5` 仍然是三轮里最稳的点
- 继续往下调 learning rate 并没有解决关键问题
- `5e-6` 明显失稳

这很重要，因为它说明当前矛盾不在“learning rate 还不够低”。

### 3. Part 33：partial_coverage 定向补样

团队又做了一个很自然的尝试：

- 既然问题集中在 partial coverage
- 那就做一小批 partial patch 补样

结果证明：

- 小规模定向补样可以修个别 raw case
- 但不能稳定泛化到 strict 改写 case
- 同时还会在其他 partial case 和 must-answer case 上引入新的副作用

因此最终组织结论是：

- `0.6B full` 保留为“风格探索支线”
- 不替代 `0.6B LoRA`
- 不影响 `1.7B` 的主部署路线

这个结论非常成熟，因为它清楚地说明了一条实验线的价值边界，而不是强行把它吹成主线。

### 1. 原始 80 题 benchmark

这套 benchmark 的意义是：

- 在当前任务分布下，看模型是否学会“按证据回答”

其结果说明：

- `1.7B LoRA` 非常强
- 在这个高约束任务里，甚至接近或超过多个 8B 到 32B 的云端模型

但团队自己也明确提醒：

- 原始 benchmark 与训练问题有较高重叠
- 不能把这个结果直接外推为开放域通用能力

这是比较负责任的写法。

### 2. strict 无泄漏 benchmark

为了避免“只会答见过的题”，团队又构建了更严格的评测集：

- 去重
- 改写
- OOD 扩充

strict v3 的结果说明：

- `1.7B LoRA` 仍然是当前最稳的质量基线
- `1.7B merged` 在任务指标上接近，但体验稍弱
- `0.6B LoRA` 没崩，但更适合轻量备用，不适合作为唯一主线
- `1.7B Q4/Q5` 量化版本的行为差异，需要单独分析，不能简单看体积或平均分

### 3. 新增未见数据 OOD benchmark

这是整套评测里最有现实意义的一层，因为它直接取自训练后新增的真实数据。

报告给出的关键数字包括：

- 总题数：24
- 可计分题：18
- `retrieval_ok_rate = 0.6111`
- 被 retrieval 卡死：`7 / 18`

这里最重要的发现有两个：

1. 当前第一瓶颈是 retrieval，而不是模型生成。
2. 一旦 retrieval 正确，`1.7B LoRA` 和 `1.7B Q5_K_M + imatrix` 基本打平。

同时也明确暴露出：

- `0.6B LoRA` 在新数据 + partial coverage + 复合对象场景下明显更脆

### 4. 空间关系高难 benchmark

这套 benchmark 的价值不是分出“谁最强”，而是定位链路瓶颈。

结论非常明确：

- 当前空间题几乎没有真正进入“比较模型能力”的阶段
- 本地和云端都被 route / formatter 压成类似输出
- 所以空间题目前不是参数量问题，而是链路没把问题送到正确通道

这个发现非常重要，因为它避免了团队把问题错误归因到“再训一轮模型”。

## 十二、从所有文档交叉看，最重要的发现有哪些

这一部分不是简单复述，而是把多份文档对齐后能得出的核心判断集中写出来。

### 发现 1：当前最稳的质量基线仍然是 1.7B LoRA

无论看：

- 原始 80 题 benchmark
- strict 无泄漏 benchmark
- 多版本综合横评

`1.7B LoRA` 都是当前最稳的“任务纪律型”版本。

它的特点是：

- 幻觉率低
- partial coverage 纪律性强
- 显式否定做得比较完整
- strict 集最稳

所以它更像“研发质量标尺”。

### 发现 2：当前最适合作为部署主线的是 1.7B Q5_K_M + imatrix

这不是因为它在所有评测里都绝对第一，而是因为：

- 它已经 GGUF 化
- 已经和 Flutter 的 `llamadart` 接法匹配
- `Q5` 的 strict 回退已经通过 `imatrix` 大幅修复
- 在 OOD frozen 口径下，它已经与 `1.7B LoRA` 非常接近，甚至略优

因此从“真实产品推进”角度，它是当前最合理的主线。

### 发现 3：0.6B 是有价值的轻量路线，但不是当前主战力

`0.6B LoRA` 的价值在于：

- 更小
- 仍可运行
- 是值得保留的轻量备选

但所有文档对齐后，结论也很清楚：

- 在新数据、partial coverage、复合对象、strict 纪律性这些维度上，它明显不如 1.7B

所以当前更适合把它看成：

- 轻量备用
- 后续压缩方向
- 资源受限时的折中路线

而不是默认主线。

### 发现 4：0.6B full SFT 更像风格探索，而不是主线替代者

`0.6B full` 的主要收益是：

- 表达更自然
- 更像产品短句

但它没有稳定打赢 `0.6B LoRA`。
尤其在 partial coverage 相关场景下，仍有泛化不稳的问题。

因此它的最终组织定位很明确：

- 保留为风格探索支线
- 不替代 LoRA 主线

### 发现 5：真正拖后腿的第一瓶颈已经不只是模型

这是所有材料里最关键的一点。

当前真正的核心瓶颈主要在：

- retrieval 对新 object / alias / recent 漂移的稳定性
- query routing 是否把问题送到正确通道
- formatter 是否能把检索结果转成正确的人话回答

也就是说：

- 继续盲目多训几轮 SFT，不一定能解决最痛的问题

### 发现 6：空间题当前还不是“模型不够聪明”，而是链路没送对地方

空间关系高难 benchmark 清楚地表明：

- 模型之间几乎没拉开差距
- 不是因为大家一样强
- 而是因为问题在 route / formatter 层就被处理成了普通场景摘要

因此空间题的后续重点，应该是：

- 建立 `spatial_relation` 专用路由
- 建立专用 formatter
- 或补上更合适的结构化检索能力

而不是先盲目加大模型。

### 发现 7：团队对“评测自欺”风险的警惕比较强

这条线里反复出现以下自我修正：

- 承认原始 benchmark 与训练分布重叠高
- 增补 strict 无泄漏 benchmark
- 冻结 retrieval 快照
- 审计 recent scene 覆盖率
- 扩容 benchmark
- 补全本地版本矩阵

这说明团队并没有只追“好看的分数”，而是在努力让评测更可信。

## 十四、当前还存在的主要风险和限制

虽然这条线已经很成熟，但仍然有若干明确风险。

### 风险 1：retrieval 实时数据漂移会影响评测稳定性

文档已经明确提到：

- Supabase 数据库在评测期间仍会新增数据
- 这会影响 `recent_list / recent_capture` 类问题

所以如果不冻结快照：

- 同一模型在不同时间跑出的结果可能不同

这也是为什么团队后来补了快照复现机制。

### 风险 2：新对象 lexical alias 仍不稳

例如文档中提到的：

- `猫咪` vs `橘白猫`
- `斑马涂鸦`
- `手冲咖啡`

这些自然问法暴露出：

- 当前 retrieval 的 alias 和 lexical 泛化仍有明显短板

### 风险 3：空间关系题还没有真正进入模型比较阶段

这类题现在更像“链路未就绪”，而不是“已经充分优化后的能力差距”。

因此如果过早把空间题失败解释成模型上限，很可能是误判。

### 风险 4：部分文档对“是否并入正式主流程”的口径存在阶段差异

例如：

- [技术栈清单.md](/ltx-data/BrainDance/docs/02-架构设计/技术栈清单.md) 仍写“尚未并入正式业务主流程”
- 而 README 与 Part 29/30 已写“当前部署主线已确定”

这更像是状态快速推进下的文档先后差，而不是逻辑冲突。
但如果对外统一口径，需要再做一次收敛。

### 风险 5：0.6B 支线若被误读，容易造成资源判断偏差

目前文档已经很清楚地表明：

- `0.6B` 有价值
- 但不等于已经可以替代 `1.7B`

如果只看某些单点指标，容易误判“0.6B 已经足够好”，这需要结合 strict、OOD 和 partial 场景一起看。
