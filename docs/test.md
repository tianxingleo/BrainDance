# 测试计划

## 测试策略与目标

### 测试重点

**前端交互：**对用户核心交互流程进行全面测试，检验前端的引导效果、交互的合理性和软件功能的易用性。

**数据链路：**对数据链路的整体和局部进行测试，检验数据链路的完整性、稳定性和时效性。

### 测试难点

**语义检索准确性：**语义检索的准确性测试需要大量的测试素材，需要投入较多的时间成本，且针对准确性的量化评估需要采集摄像头位置等数据，工作量较大。

**3dgs 模型的生成质量：**不同设备和不同拍摄方式导致拍摄质量参差不齐，而拍摄质量则会对 3dgs 模型的生成质量产生大程度的影响，在测试时需要维持较高的拍摄质量以确保较优生成质量，这一点需要投入较多时间成本，且较难对生成质量进行量化评估。

**数据安全与隔离：**测试后端数据库是否存在越权访问等安全风险，难点在于安全测试需要构造 "攻击者视角" 的用例且测试难以完全自动化。

### 测试分层

粒度由细到粗依次为：单元测试、功能测试和系统测试。

**单元测试：**针对独立的函数、方法或 UI 组件进行隔离测试，通过桩件（mock/fake）替换外部依赖，验证被测单元内部逻辑的正确性。典型粒度为单个函数（如 `_contains_emoji`、`_build_cpu_fallback_cmd`）或单个 Widget（如 `RecallModelGrid`）。

**功能测试：**针对完整的功能链路和模块间协作进行端到端验证，包括脚本编排、HTTP 接口调用、数据库读写、状态变更和 Agent 交互等，验证各功能在真实或接近真实环境下的行为是否符合需求。

**系统测试：**从整体系统角度进行测试，验证系统的性能指标、资源占用和稳定性，评估系统在接近生产条件下的可用性。

### 测试目标

检验该项目是否达到 Level 3 可发布等级，要求前端交互完备，核心路径通过率大于 99%，无 P0 / P1 bug，语义检索准确性和 3dgs 模型的生成质量能不影响用户正常使用，数据安全与隔离完备。

## 测试范围

### 测试广度

测试广度从多维度展开，主要包括设备环境、网络环境及输入条件等方面。通过覆盖不同移动端设备对前端 UI 排布的影响，不同网络状态（如断开、延迟）对数据链路稳定性的影响，以及不同拍摄时长对 3dgs 模型生成质量与生成效率的影响，从多个维度验证系统在不同使用场景下的适应能力与稳定性。

### 测试深度

测试深度采用逐层递进的方法进行设计。在基础功能验证的基础上，通过高频交互测试提升操作压力，通过对数据链路中间数据的检验增强系统可观测性，并通过重复操作与异常场景测试对系统稳定性进行验证，从而逐步覆盖边界条件、异常情况及高压力场景，确保系统在复杂环境下仍能稳定运行。

| 用例编号 | UT-06 |
| 测试单元描述 | _searchModels 在连续两次异步搜索中仅保留最新请求结果，旧请求即使后返回也不能覆盖页面状态。 |
| 用例目的 | 验证 _searchRequestId 的并发防抖语义，避免快速输入时列表闪回到旧结果。 |
| 前提条件 | 1. 两次搜索使用不同关键字。2. 第一条请求故意延迟完成。3. 第二条请求先完成并写入结果。 |
| 特殊的规程说明 | 1. 使用 Completer<List<Map<String, dynamic>>> 控制返回顺序。2. 断言第二次结果最终保留在 _models。3. 第一条请求完成后再次断言结果未被覆盖。 |
| 用例间的依赖关系 | 依赖 UT-04 的可控异步搜索桩。 |

| 具体步骤 | 输入 | 期望输出 | 实际输出 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 连续发起两次不同关键词搜索，并故意让第一请求晚于第二请求返回。 | 第二请求先完成并写入结果。 | 第二次关键词搜索结果先写入 _models。 | 无 |
| 2 | 等待第一请求延迟返回。 | 旧请求结果不能覆盖当前页面状态。 | 第一请求返回后未覆盖当前 _models 中的第二次搜索结果。 | 无 |


测试结果分析：

该用例针对并发搜索场景中的状态污染风险。实际结果说明，系统能够只保留最新请求的结果，旧请求即使后到也不会覆盖当前页面状态，说明 _searchRequestId 或等价的并发保护机制已经生效。对于快速输入、连续检索这类高频场景，这是保障用户看到最新结果的关键能力。

**缺陷记录（BUG-001，P2，已修复）：** 首轮测试中步骤 2 失败——第一请求延迟返回后覆盖了第二请求的结果，导致页面闪回旧列表。根因为 `_searchRequestId` 的比较发生在 `await` 之后，而该字段在等待期间已被第二次调用更新，导致守卫条件失效。修复方案：在发起异步搜索前将当前 `_searchRequestId` 捕获到局部 `final` 变量，`await` 返回后与局部变量比较而非与实例字段比较。复测通过。

### 测试结果综合分析及建议

从本轮测试结果看，前端组件与搜索状态机相关的 10 个单元测试用例在"资产卡片渲染、搜索状态分流、导航回调参数"三个维度上表现稳定。所有用例均通过 testWidgets 或 test 隔离执行，不依赖真实网络请求，验证的是单个 Widget 或单个状态转换函数的内部逻辑正确性。

具体来看，RecallModelGrid 组件的浏览态渲染用例验证了标题字段的优先级兜底逻辑与点击回调参数传递，说明该组件在面对字段不完整数据时仍具备基本可用性。搜索状态机相关用例重点验证了 _searchModels 函数的模式分流、缓存命中、_searchRequestId 并发保护和 _handleSearchSubmitted 的提交分流，这些结果说明各状态转换函数的内部逻辑正确。导航回调用例覆盖了 toPublicUrl / toPosesUrl 的 URL 推导和帧级 transform_matrix 的优先级处理，结果表明参数组装函数的行为符合预期。

不过，当前通过结果更多反映的是既定脚本覆盖范围内的正确性，并不等同于模块已经穷尽所有风险。后续建议继续补充以下几个方向。第一，增加边界数据测试，例如空数组、字段缺失、异常格式 transform_matrix、无效 ply_path、非法 meta_info 等输入，进一步验证容错能力。第二，增强异常链路测试，尤其是云端搜索失败、索引超时、Agent 返回结构不完整、Viewer 页面打开失败等场景，避免当前测试过度集中在成功路径。第三，补充更接近真实使用过程的组合场景测试，例如"连续搜索后立即跳转 ""搜索清空后再次进入 Agent 模式"" 缓存命中后切换模式重新搜索"等，以验证状态机跨流程切换时的稳定性。第四，可以逐步建立回归测试清单，把当前已验证的 10 个用例固化为回归基线，在后续页面重构或搜索逻辑调整时自动复跑。

从工程实现角度看，搜索逻辑相关测试仍然明显依赖页面状态与 Harness 驱动，这意味着当前业务状态机与 UI 耦合度仍偏高。建议在后续迭代中继续推进搜索控制逻辑下沉，将 _searchModels、缓存判断、请求保护、提交分流等逻辑抽离为独立控制器或协调器。这样不仅能提高单元测试执行效率，也能降低界面组件测试的维护成本，提升后续缺陷定位速度。

### 测试经验总结

本次测试工作的一个直接经验是，先划清"浏览展示 ""搜索状态"" 定位跳转"三个子域，再分别设计基线用例和增强用例，会比按页面元素零散列点更容易形成闭环。这样的拆分方式有助于在编写测试时明确每个用例究竟是在验证展示逻辑、状态机逻辑还是导航逻辑，也方便后续问题追溯。

第二个经验是，涉及搜索与异步交互的前端模块，不能只测结果列表是否出现，还必须同步验证调用路径、缓存是否命中、旧请求是否被抑制、模式切换是否串路。单看页面最终展示，往往无法发现本地搜索误走云端、旧请求回写覆盖新结果这类更隐蔽的问题。本轮测试之所以能较完整覆盖搜索能力，关键就在于把"调用行为"和"页面结果"同时纳入断言。

第三个经验是，定位跳转相关测试应同时关注参数来源和参数优先级，而不仅仅是"能否打开 Viewer"。例如普通浏览态应使用默认位姿，搜索结果态应优先使用帧级矩阵，Agent 场景则要同时校验正常动作和缺失字段时的防御行为。只有把这些差异化路径都显式纳入测试，才能真正证明定位链路是可信的。

第四个经验是，测试文档结构会直接影响结果复用效率。本轮将每个用例拆成步骤表，并补充逐条分析后，文档已经不仅是结果登记材料，也可以直接作为后续回归测试、评审答辩和问题复盘的依据。后续建议继续保持"步骤化记录 +用例分析 +综合总结"的文档方式，这样在需要补测、复测或交接时，信息更完整，也更便于外部人员理解。

### 测试结果综合分析及建议

从本次执行结果看，流水线核心函数与工具方法的 16 个单元测试用例均通过，覆盖了 _contains_emoji、_record_cloud_log、_build_cpu_fallback_cmd、_command_uses_gpu、_run_cmd、GPU 索引映射、端口解析、SceneAnalyzer 结果归一化等独立函数的内部逻辑。所有用例均通过 monkeypatch 或 fake 对象隔离了外部依赖，验证的是单个函数的输入输出行为和边界条件处理，符合单元测试的粒度要求。

综合判断，这批核心函数当前处于"主体逻辑稳定、个别数学细节待核验"的状态。16 个用例全部通过，说明各函数的基础行为正确；但尚未达到"全量入口可持续回归"和"关键数学逻辑完全闭合验证"的理想状态。

建议对现有测试进一步分层管理。依赖外部服务的脚本和手工脚本应与纯函数级单元测试分开维护，避免在统一入口下相互干扰。单元测试目录中如果继续混入外部依赖较强的脚本，会降低回归效率，也容易造成测试结果解释混乱。

建议在后续回归中保留"全量入口执行 +逐项补充执行"的双层策略。全量入口适合发现导入错误、环境问题和测试间耦合问题；逐项执行适合定位具体业务逻辑是否正确。两者结合，能够更完整地反映模块真实质量状态。

### 测试经验总结

本次测试说明，在持续演进的项目中，测试代码与业务代码一样需要同步维护。历史测试一旦脱离当前目录结构和模块命名规则，就会从"质量保障资产"变成"回归阻塞点 "。因此，代码重构后同步更新测试路径和依赖，是保持测试体系有效性的必要工作。

本次测试还表明，把复杂模块拆成可独立执行的小粒度单元测试是有效的。虽然全量入口被单个文件阻断，但通过逐项执行，仍然能够较完整地评估模块的大部分能力，这种方法在处理老项目、混合测试项目和依赖复杂项目时尤其有价值。

从 GPU 索引映射相关用例（UT-17 至 UT-19）的结果可以看到，数学类逻辑的测试不能只验证最终流程是否跑通，还需要对关键中间结果建立更细的断言，尤其是涉及坐标变换、姿态表示、矩阵或四元数计算时。若断言粒度过粗，问题会被掩盖；若断言口径不严谨，则可能把等价结果误报为失败。

从日志处理、端口分配和命令回退相关用例的通过情况来看，针对边界条件、异常路径和回退路径设计测试，往往比只验证主流程更能体现单元测试价值。本次通过的多数用例正是覆盖了失败回退、空值输入、端口冲突、格式异常等场景，因此结果的参考价值较高。

总体经验是，单元测试文档不仅要记录"是否通过 "，还要说明"失败发生在哪一层 ""失败是否反映真实业务缺陷""测试本身是否仍然有效"。只有把测试结果、原因分析和后续建议一起沉淀下来，测试文档才能真正支撑后续整改与复测。

其中，FT-01 和 FT-02 验证了 search-models 语义检索接口的参数校验和统一分发能力，是检索链路从 dry-run 迈向真实 HTTP 的关键一步。FT-03 到 FT-05 验证了 NDJSON 和 SSE 两种流式协议的可用性与事件序列完整性，FT-06 和 FT-07 构成了 preview/execute 对照组，证明了写操作确认链路的安全性。FT-08 到 FT-10 则从 AI 特有风险角度出发，分别覆盖了上下文截断、Prompt 注入和幻觉写入三类典型攻击场景。FT-11 在飞行模式下验证了端侧本地 AI 离线语义检索能力，FT-12 验证了 3DGS Viewer 的手势交互流畅性，FT-13 则在真机上完成了 Agent 对话式回忆检索的全链路闭环。

后续建议继续在以下方面加强。第一，Prompt 注入测试的覆盖范围可以进一步扩展，例如加入间接注入（通过模型 display_name 嵌入恶意指令）和多语言注入变体。第二，上下文截断测试建议增加真正超出 Token 上限的场景，验证 Agent 在强制截断后的行为是否仍然可控。第三，幻觉防御目前仅验证了空表场景，建议补充"表中存在数据但查询条件不匹配"的场景。第四，对端侧 AI 的内存占用和电池消耗进行量化测试。第五，语音输入作为 Agent 模式的等价入口，建议后续补充语音识别准确率测试。

### 测试经验总结

本轮测试最重要的经验是，对于 AI Agent 类功能，传统的接口测试（HTTP 状态码、响应结构校验）是必要但不充分的。需要额外设计针对 AI 特有风险的测试用例，包括上下文处理边界、恶意输入防御和幻觉行为控制。这类测试的设计思路与传统功能测试有本质差异——不是验证"能否做到"，而是验证"不该做的时候能否不做"。

第二个经验是，preview/execute 双模式设计在测试中体现出很高的价值。通过强制所有写操作先走 preview 再走 execute，测试可以在 preview 阶段安全地验证 Agent 的操作意图识别能力，而不用担心误操作污染数据库。FT-06 到 FT-09 都利用了这一设计，使得安全类测试可以放心执行。

第三个经验是，幻觉防御测试需要构造"诱导但不满足"的前提条件。FT-10 通过清空模型表制造了一个"用户意图明确但无可操作目标"的场景，这正是 Agent 最容易产生幻觉的条件。这种"设陷阱"式的测试设计比简单的功能验证更能暴露 AI 系统的深层问题。

第四个经验是，回忆检索能力的测试需要同时覆盖"在线"和"离线"两种模态。FT-11 的飞行模式测试和 FT-13 的在线 Agent 测试形成互补，证明了应用在有网和无网条件下都能提供 AI 辅助检索能力。这种双模态设计是移动端 AI 应用区别于纯云端 AI 服务的关键差异点。

第五个经验是，模型查看交互测试不能仅关注"能否打开"，还需关注手势响应的流畅度和多设备一致性。FT-12 通过在不同厂商设备上量化帧率，为后续优化提供了可比较的基线数据。

### 测试结果综合分析及建议

从 FT-20 至 FT-22 三项端侧 AI 模型评测的结果来看，模型选型与量化部署策略在"综合指标对标、未见数据泛化、量化版本精选"三个维度上均形成了闭环结论。

FT-20 通过全模型热力图确认了 1.7B LoRA 微调模型的综合表现领先，并量化证明了工程优化增益大于单纯增加参数量。FT-21 通过 Frozen 快照机制排除检索漂移干扰后，发现 Q5+iMatrix 量化版本在真实未见数据上以 0.9167 的通过率略微领先 LoRA 原版的 0.8333。FT-22 进一步揭示了 iMatrix 对 Q5_K_M 量化退化的针对性修复效应，最终确立了 Q5_K_M + iMatrix 作为端侧部署主线的版本选型。

后续建议在以下方面继续深化。第一，随着评测集规模扩大，定期重跑热力图以监控模型表现是否退化。第二，补充更多 OOD 数据的泛化评测批次，验证 Q5+iMatrix 的泛化优势是否具有统计显著性。第三，在真机上对 Q5_K_M+iMatrix 进行推理延迟和内存占用的量化测试，确认其在实际端侧硬件上的部署可行性。第四，建立量化版本的自动化回归评测流水线，在每次模型更新或 iMatrix 校准数据变更后自动触发评测。

### 测试经验总结

本轮评测最重要的经验是，模型评测必须消除上游因素（如检索漂移）的干扰才能得到可信结论。FT-21 中 Live 与 Frozen 环境的对比清楚表明，如果不采用快照机制，线上数据库的持续扩容会严重干扰模型排序的准确性。这一方法论适用于所有涉及 RAG 链路的模型评测。

第二个经验是，量化精度与任务表现之间的关系不是单调的。FT-22 揭示了 Q5 常规量化反而不如 Q4 的违反直觉现象，只有叠加 iMatrix 后才恢复预期表现。这说明量化部署不能简单地选择"最高可承受精度"，还需要通过实际评测验证任务指标是否退化。

第三个经验是，多维度评测报告的可视化形式直接影响决策效率。热力图、柱状对比图和折线图分别适用于"全模型横向对标""环境差异对比"和"策略前后变化追踪"三种决策场景，选择正确的可视化形式能让结论更快被团队理解和采纳。

测试结果分析：

ST-04 的实际结果表明，在 RTX 4090 + 64GB RAM 环境下，标准 30 秒视频的重建流水线资源峰值在硬件承载范围内。GPU 显存峰值出现在 3DGS 训练阶段，约 13.2GB，占 24GB 总显存的 55%，仍有较大余量。系统内存峰值 18.4GB，不到总量的 30%。全流程未出现 OOM 或显存不足错误。后续建议针对 60 秒和 120 秒长视频进行扩展测试，验证资源占用的增长趋势是否仍在可控范围内。

### 测试结果综合分析及建议

从 4 项性能测试的结果来看，系统在标准测试条件下各项性能指标均满足预期目标。3DGS 模型生成端到端耗时 11 分 42 秒，在 15 分钟目标内留有约 22% 余量；语义检索响应延迟在不同复杂度的 query 下均控制在 3 秒以内；首屏加载时间 1.23 秒，保持了 60fps 无掉帧的渲染质量；GPU 峰值显存占用约为硬件总量的 55%，资源余量充足。

不过，当前性能测试的输入条件偏向理想化。视频时长仅 30 秒、资产规模仅 50 条、网络环境为局域网，这些条件与实际用户场景之间存在差距。后续建议在以下方面扩展性能基线。第一，增加 60 秒和 120 秒视频的重建耗时测试，验证耗时增长是否接近线性。第二，将资产规模从 50 条扩展到 200 条和 500 条，验证语义检索和列表加载的性能退化曲线。第三，在 4G/5G 真实移动网络环境下重新测试首屏加载和检索延迟。第四，增加并发场景测试，例如两个用户同时提交重建任务时的 GPU 资源争用与排队策略。

### 测试经验总结

本轮性能测试的核心经验是，分阶段记录比只看端到端总耗时更有价值。ST-01 通过分段记录四个阶段的耗时，清晰定位了特征匹配和 3DGS 训练是耗时瓶颈。如果只记录总耗时，后续优化就缺乏方向。建议后续所有性能测试都采用分段记录策略。

第二个经验是，性能测试必须同时记录绝对值和余量比。例如显存峰值 13.2GB 本身不足以判断是否安全，但对比 24GB 总量后可知余量约 45%，这才是决策的关键信息。后续建议在性能测试报告中统一标注"实际值/上限值/余量比"三列。

第三个经验是，不同复杂度的输入对性能的影响差异较大。ST-02 显示简单 query 与复杂 query 的延迟差异超过 100%，这说明性能基线必须覆盖多种典型输入，单一输入的测试结果代表性不足。后续建议建立"标准性能测试输入集"，包含简单、中等、复杂三档典型输入，在每次性能回归中统一使用。

从 4 项移动端兼容性与稳定性测试的结果来看，应用在多设备适配、多厂商一致性、长时间内存稳定性和前后台切换恢复四个维度上均达到可接受标准。UI 适配在 4 台不同规格设备上整体良好，中低端设备性能虽有下降但仍在可用范围内；多厂商功能一致性验证了 Flutter 方案在不同 Android 定制系统上的兼容性；30 分钟连续操作未暴露内存泄漏；前后台切换的状态恢复和推送通知在各设备上均表现正常。

后续建议在以下方面扩展。第一，增加更多中低端设备的覆盖，尤其是 4GB RAM 以下的设备，验证内存压力下的应用行为。第二，将稳定性测试时长延长至 60 分钟甚至更长，更充分地验证内存增长趋势。第三，补充 Android 不同版本（Android 11/12/13/14）的兼容性验证，确保不存在特定版本的 API 兼容问题。第四，增加后台被系统强杀后的冷恢复测试，验证用户数据不会因系统回收而丢失。

### 测试经验总结

本轮测试的核心经验是，移动端的"兼容性"不仅仅是 UI 不错位，还包括性能在不同设备上的降级表现。ST-05 的中低端设备测试显示，首屏加载和 Viewer 帧率与旗舰设备差距显著，这意味着后续需要考虑根据设备性能动态调整渲染策略。单纯验证"能不能跑"是不够的，还需要验证"跑得够不够好"。

第二个经验是，前后台切换测试必须覆盖多个时长档位。ST-08 的结果显示，10 秒、1 分钟和 5 分钟后台分别触发了不同的系统行为（完整保留、静默刷新、系统回收后重建）。如果只测 10 秒后台，就会遗漏华为等厂商系统内存管理策略导致的 App 重建恢复路径问题。

第三个经验是，内存稳定性测试需要关注增长曲线的形状而非绝对值。ST-07 显示 30 分钟后内存增长 36.3%，单看这个数字似乎偏高，但增长曲线趋于收敛且 GC 后能有效回收，这说明不存在内存泄漏。如果增长曲线是线性的，即使绝对增量更小也更值得担忧。

### 测试结果综合分析及建议

从本轮 4 个系统测试用例的结果看，系统在并发重建、跨用户隔离、Agent Chat 长会话和社区规模化加载四个新增风险面上均达到可接受标准。ST-09 验证了多人同时提交重建任务时的队列和 GPU 资源保护能力；ST-10 验证了资产、社区和 Agent 会话在真实多账号场景下没有发生越权访问；ST-11 验证了 Agent Chat 在长会话和流式响应下的稳定性；ST-12 验证了社区功能在 1000 条帖子规模下的移动端性能下限。

后续建议继续扩展两个方向。第一，将 ST-09 的并发规模从 5 用户提升到 10 用户和 20 用户，观察排队等待时间、任务成功率和 GPU 资源余量。第二，将 ST-12 的社区数据规模扩展到 5000 条，并增加弱网图片加载场景，验证分页、地图标记选择和图片缓存策略的退化曲线。

### 测试经验总结

本轮测试的核心经验是，新增功能进入系统测试阶段后，重点不应只看单个功能能否完成，而要验证它们在真实系统压力下是否仍能守住边界。社区和 Agent Chat 都涉及用户生成内容、会话状态和跨用户数据访问，如果只做功能测试，很难暴露规模化加载、长会话状态膨胀和权限串号问题。

第二个经验是，并发测试需要同时观察业务结果和资源指标。ST-09 不仅检查任务是否完成，还记录了 GPU 显存峰值和队列行为，这样才能判断系统是稳定承载了并发，还是只是偶然没有失败。

第三个经验是，安全隔离必须做后端和数据库层验证。ST-10 显示，前端页面不展示他人数据并不等于系统安全，只有通过伪造请求和数据库事后校验，才能确认 RLS 与服务端鉴权真正生效。
