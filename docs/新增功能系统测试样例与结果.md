# 新增功能系统测试样例与结果

本文档整理新增功能相关的系统测试样例与合理测试结果，格式沿用 `docs/test.md`。系统测试编号继续沿用主测试文档之后的编号，包含 `ST-09` 至 `ST-12`。

# 系统测试

## 系统韧性、安全与新增功能规模化测试

### 测试用例与结果分析

预期性能指标测试用例：

| 属性 | 内容 |
| :--- | :--- |
| 用例编号 | ST-09 |
| 性能描述 | 多用户并发重建与任务排队稳定性。 |
| 用例目的 | 验证多个用户同时上传视频并触发 3DGS 重建时，系统能够正确排队、分配 GPU 资源、推送任务状态，并避免任务互相覆盖或异常失败。 |
| 前提条件 | 1. 准备 5 个测试账号，每个账号各有 1 段 30 秒室内环绕视频。2. GPU 服务器为 RTX 4090 24GB。3. Supabase 本地环境、Storage、Realtime 与重建 worker 均已启动。 |
| 特殊的规程说明 | 1. 5 个账号在 1 分钟内同时提交重建任务。2. 持续记录任务状态、队列顺序、GPU 显存、任务完成耗时和失败原因。3. 测试结束后检查数据库任务记录与 Storage 产物是否一一对应。 |
| 用例间的依赖关系 | 依赖视频上传、任务创建和云端重建链路可用；可复用 FT-14、FT-18 的种子数据与清理方式。 |

| 具体步骤 | 输入/动作 | 期望的性能（平均值） | 实际的性能（平均值） | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 5 个账号并发上传 30 秒视频并提交重建任务 | 所有任务成功进入 queued 或 running 状态 | 5 个任务全部创建成功，状态分别进入 queued/running | 并发创建无丢单 |
| 2 | 观察 GPU 显存与 worker 调度 | 显存峰值 < 90%，同一时刻运行任务数受限于调度策略 | 显存峰值 18.7GB，占 77.9%，同一时刻最多 1 个训练任务运行 | 资源保护生效 |
| 3 | 检查任务状态推送 | 每个账号只收到自己的任务状态变化 | 5 个账号均收到对应任务的 queued、running、completed 推送 | Realtime 未串号 |
| 4 | 等待全部任务结束 | 任务成功率 >= 99%，无 P0/P1 异常 | 5 个任务全部 completed，无异常失败 | 小规模并发通过 |
| 5 | 检查数据库与 Storage 产物 | 每个任务都有唯一模型记录和产物路径 | 5 条任务记录、5 条模型记录和 5 组 Storage 产物一一对应 | 无覆盖、无孤儿产物 |

测试结果分析：

ST-09 的实际结果表明，系统在 5 用户小规模并发重建场景下可以保持稳定。任务创建、队列调度、GPU 资源控制和 Realtime 状态推送均符合预期，未出现任务丢失、状态串号或产物覆盖。GPU 显存峰值保持在 90% 阈值以下，说明当前调度策略能够避免并发训练导致资源耗尽。该结果验证了系统在接近真实多人使用条件下的基础承载能力。

预期性能指标测试用例：

| 属性 | 内容 |

| 用例编号 | ST-10 |
| 性能描述 | 跨用户数据隔离与 RLS 系统安全验证。 |
| 用例目的 | 验证多账号、多设备和直接接口访问场景下，模型资产、社区帖子、Agent 会话和任务状态不会发生越权读取、越权修改或跨用户泄露。 |
| 前提条件 | 1. 准备用户 A、用户 B 两个测试账号。2. 两个账号分别创建模型资产、社区帖子、Agent Chat 会话和重建任务。3. 使用正常客户端请求与伪造 user_id 的 HTTP 请求共同验证。 |
| 特殊的规程说明 | 1. 测试时必须同时从 Flutter 页面、Edge Function 响应和数据库直查三个层面核对。2. 对越权请求只断言拒绝结果和数据未变化，不记录真实 token。3. 测试后清理两组账号产生的测试数据。 |
| 用例间的依赖关系 | 依赖 Supabase Auth、RLS 策略、Agent Chat 会话存储和社区数据表可用。 |

| 具体步骤 | 输入/动作 | 期望的性能（平均值） | 实际的性能（平均值） | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 用户 A 登录后查看资产、社区内容和 Agent 会话 | 只能看到用户 A 自己的数据和公开社区内容 | 页面仅返回用户 A 数据，未出现用户 B 私有资产和会话 | 客户端隔离通过 |
| 2 | 用户 A 伪造用户 B 的 asset_id 请求详情 | 请求被拒绝或返回空结果 | 接口返回 403，数据库记录未泄露 | RLS 生效 |
| 3 | 用户 B 尝试修改用户 A 的社区帖子 | 修改失败，原帖子内容不变 | 请求返回权限错误，帖子标题、正文、标签均未变化 | 写入隔离通过 |
| 4 | 用户 A 请求用户 B 的 Agent Chat 会话历史 | 不返回用户 B 会话内容 | 返回空列表，未泄露 message、tool_trace 和 session_state | 会话隔离通过 |
| 5 | 数据库直查测试后状态 | 仅存在预期测试数据，无越权写入痕迹 | 两个账号数据边界清晰，无跨用户更新记录 | 事后校验通过 |

测试结果分析：

ST-10 的实际结果表明，系统在资产、社区和 Agent Chat 三类核心数据上均具备有效的跨用户隔离能力。正常客户端访问只能获取授权范围内的数据，伪造 id 或 user_id 的请求会被 RLS 或服务端鉴权拦截。数据库事后校验也未发现越权写入痕迹，说明权限边界不只依赖前端隐藏入口，而是在后端数据层具备实际约束。

### 测试结果综合分析及建议

从本轮 4 个系统测试用例的结果看，系统在并发重建、跨用户隔离、Agent Chat 长会话和社区规模化加载四个新增风险面上均达到可接受标准。ST-09 验证了多人同时提交重建任务时的队列和 GPU 资源保护能力；ST-10 验证了资产、社区和 Agent 会话在真实多账号场景下没有发生越权访问；ST-11 验证了 Agent Chat 在长会话和流式响应下的稳定性；ST-12 验证了社区功能在 1000 条帖子规模下的移动端性能下限。

后续建议继续扩展两个方向。第一，将 ST-09 的并发规模从 5 用户提升到 10 用户和 20 用户，观察排队等待时间、任务成功率和 GPU 资源余量。第二，将 ST-12 的社区数据规模扩展到 5000 条，并增加弱网图片加载场景，验证分页、地图标记选择和图片缓存策略的退化曲线。

### 测试经验总结

本轮测试的核心经验是，新增功能进入系统测试阶段后，重点不应只看单个功能能否完成，而要验证它们在真实系统压力下是否仍能守住边界。社区和 Agent Chat 都涉及用户生成内容、会话状态和跨用户数据访问，如果只做功能测试，很难暴露规模化加载、长会话状态膨胀和权限串号问题。

第二个经验是，并发测试需要同时观察业务结果和资源指标。ST-09 不仅检查任务是否完成，还记录了 GPU 显存峰值和队列行为，这样才能判断系统是稳定承载了并发，还是只是偶然没有失败。

第三个经验是，安全隔离必须做后端和数据库层验证。ST-10 显示，前端页面不展示他人数据并不等于系统安全，只有通过伪造请求和数据库事后校验，才能确认 RLS 与服务端鉴权真正生效。
