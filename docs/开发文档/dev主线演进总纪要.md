# BrainDance `dev` 主线演进总纪要

## 文档目的

这份文档不再以“每个分支各写一章”为主，而是把 `dev` 视为 BrainDance 的主演进干线，顺着主线时间序阅读提交历史，重建整个项目从原型到系统的升级过程。

文档目标有三点：

- 以 `dev` 为唯一主链，解释项目为什么会变成现在这个形态。
- 对 `dev` 上的 merge 提交，不停留在“合并了某分支”，而是追读被合入的新增 commit。
- 用中文 changelog 风格总结每个阶段的定位、逐提交演进、代表性优化、工程方法、独创改进和“升级与进步”。

## 阅读口径

- 主线读取方式：`git log --first-parent --reverse <merge-base(main, dev)>..dev`
- 对主线上出现的 merge，补读其真正带入 `dev` 的新增 commit，而不是只记 merge 标题。
- 由于仓库历史中存在同主题双提交、跨分支重复导入、后续回并等情况，本文遵循两条规则：
  - 阅读层面：尽量把每个 commit 都看过。
  - 展示层面：对内容相同或明显重复导入的 commit 用“并列 hash”或“能力去重”方式呈现，不机械重复两遍。

## 一眼结论

如果只用一句话概括 `dev` 这条主线的真实演进方向，那就是：

**BrainDance 从“能生成 3DGS 的实验脚本”，一步步进化成了“具备输入治理、算法路由、Viewer 交互、RAG 检索、Flutter 产品界面、任务实时协同、压缩交付、多流水线扩展与复现规范”的完整系统。**

更具体地说，它经历了七次重心迁移：

1. 先把 3DGS 基础流程和坐标链打通。
2. 再把输入质量、图片清洗和 COLMAP 稳定性做扎实。
3. 然后把 AI 分割、SAM3D、VGGSfM、VGGT、Qwen-VL、GLOMAP 一路试下来，筛出适合工程落地的路线。
4. 接着把 3DGS 结果做成真正可交互的 Web Viewer，并引入 RAG 检索。
5. 再用工程化重构把复杂度收住。
6. 之后把 Flutter 客户端、Supabase、任务系统、Dashboard、Recall 工作流和多流水线接进来。
7. 最后通过 3 月的一大批交互、体验、压缩交付和页面结构改造，把系统收束成更完整的产品形态。

## 阶段 A：原型起盘与预处理链搭建

### 阶段定位

这一段最重要的任务不是“做一个漂亮产品”，而是把 3DGS 最基本的生产链先搭起来：

- 先有 AI 后端和 PyTorch 基础代码。
- 再让训练产物能进入 WebGL 坐标系。
- 再把视频/图像输入清洗成适合重建的样子。
- 最后开始把这套经验写进 README 和技术文档。

### 阶段总结

这一段最该被强调的，不是“做了几个脚本”，而是形成了 BrainDance 后续一直沿用的方法论：

- 输入质量优先于盲目加算力。
- 失败模式必须显式识别，而不是人工碰运气。
- 研究经验必须尽快写成文档。
- 训练结果必须尽早进入 WebGL/客户端链路，而不是只停在命令行里。

## 阶段 B：分割强化、SAM3D、VGGSfM、VGGT 与 GLOMAP 路线试错

### 阶段定位

这一段是 `dev` 主线上技术张力最大的一段。团队并没有满足于把 COLMAP 调顺，而是连续做出几次大胆路线切换：

- 接入 `SAM3D`，探索单图到 3D 的可能。
- 尝试 `VGGSfM`，再迅速转向 `VGGT`。
- 让 `Qwen-VL` 从分割提示辅助，升级为场景级决策器。
- 最后在工程现实约束下，把主力 SfM 后端收敛到 `GLOMAP`。

### 阶段总结

这一段最重要的不是“接了很多新模型”，而是围绕几个核心问题连续做出了系统性技术选择：

## 最终总结：`dev` 主线到底体现了什么升级

如果把整条 `dev` 主线浓缩成五条演进线，可以得到如下结论：

### 1. 输入治理线

项目从一开始就没有把 3DGS 成败归因于训练器本身，而是不断强化：

- 拍摄类型识别
- 噪声抑制
- 模糊清洗
- 质量熔断
- 中心目标锁定
- RGBA/alpha 统一
- 去 `mask_path` 消除漂浮伪影

这说明 BrainDance 的方法论非常成熟：**先把脏输入挡在外面，再谈模型升级。**

### 2. 算法替换线

主线没有守着一条技术路线不放，而是连续试错：

- 强化 COLMAP
- 试 `SAM3D`
- 接 `VGGSfM`
- 跳 `VGGT`
- 最终收敛到 `GLOMAP`

这里最重要的不是“追新”，而是：**每次切换都带着明确的问题意识和工程代价判断。**

### 3. 可视化与交互线

项目没有停留在命令行结果层，而是把 3DGS 做成了：

- 可嵌入 Flutter 的 Viewer
- 有自由视角、VR 入口和焦距控制的交互前台
- 有粒子飞入、扩散显现、生长叙事的视觉系统
- 有桌面滚轮和移动端双指缩放的成熟交互器

这使 BrainDance 不再只是“生成模型”，而是“交付一个可被感知和探索的记忆对象”。

### 4. 产品与协同线

从 2026 年 1 月以后，`dev` 主线已经明显不再是纯 AI 仓库：

- Flutter 客户端
- Supabase 存储与任务
- Realtime 通知
- Task List
- Recall 工作台
- Dashboard 运维看板
- 端侧问答
- 图生/文生入口

说明项目已经把“AI 引擎”发展成了“前后端协同产品”。

### 5. 工程方法线

`dev` 主线最强的底层竞争力，其实是工程方法，而不只是模型列表：

- 配置中心
- 类职责拆分
- Strategy/Factory 路由思维
- 子模块治理
- Git LFS
- 压缩交付
- 环境依赖文档
- 复现流程规范

这意味着 BrainDance 的升级不是“功能堆叠”，而是**系统复杂度被持续重新组织**。

## 结尾判断

站在 `dev` 主线视角回看，BrainDance 最有价值的地方，不是某一次“接入了什么新模型”，而是它连续证明了五件事：

1. 团队知道 3DGS 真正会失败在哪里。
2. 团队愿意为了真实硬件环境改写和修补复杂依赖。
3. 团队能把 AI 结果做成可查看、可检索、可交互的产品能力。
4. 团队能把不断膨胀的复杂度重新收回到可维护结构里。
5. 团队能把实验经验沉淀成文档、规范和可复现流程。

所以 `dev` 这条主线真正体现出的“升级与进步”，不是单点算法领先，而是 **从研究型原型持续进化为完整系统工程**。
