# **技术研究报告**

# 1    问题聚焦[[提示1初赛阶段完成\]](#_msocom_1) 

## 1.1 问题描述

BrainDance（流光·记）当前已经实现的核心问题，不是抽象层面的“空间计算愿景”，而是一条真实可运行的云端三维语义处理链路：用户上传视频或图片后，系统如何自动完成三维重建、结果入库以及自然语言检索。

结合当前仓库实现，项目主要解决以下问题：

1. 传统二维影像只能记录平面画面，缺乏空间结构，无法作为可检索的三维记忆资产长期保存与复用。
2. 视频到三维模型的工程链路长、失败点多，普通输入数据容易在抽帧、位姿解算、训练或上传环节中断，导致系统不可用。
3. 现有三维模型通常只有几何表达，没有语义入口，用户无法通过“宿舍”“红色杯子”“上周拍的照片”等自然语言进行检索。

## 1.2 问题抽象[[提示2将项目要解决的具体问题抽象转化为技术问题\]](#_msocom_2) 

结合当前实现，可将项目问题抽象为以下技术问题：

1. 如何构建一条面向普通视频/图片输入的云端三维重建流水线，使其自动完成抽帧、位姿解算、3DGS 训练、模型上传与任务状态同步。
2. 如何在不额外引入 Redis、独立向量数据库等中间件的情况下，基于 PostgreSQL/Supabase 同时完成任务调度、资产管理和语义检索。
3. 如何利用多模态模型生成场景描述、标签和物体信息，并将这些语义信息转换为向量表示，支撑场景级自然语言搜索。

## 1.3 问题定位[[提示3指出该问题所属的业务领域与技术领域\]](#_msocom_3) 

本项目属于“AI 无界”主题下的 AI 影像处理与空间智能交叉方向，具体涉及以下领域：

- 计算机视觉：视频抽帧、图像质量分析、SfM 位姿解算、3D Gaussian Splatting
- 多模态人工智能：图像理解、场景打标、文本向量化、自然语言意图解析
- 数据库与云计算：Serverless 架构、对象存储、实时订阅、向量检索
- 软件工程：异步任务编排、日志同步、模块化 Pipeline 设计

## 1.4 问题评估[[提示4分析问题本身的技术性、普适性、热度等特点。\]](#_msocom_4) 

1. 技术性强。当前仓库已经实际涉及 FFmpeg、GLOMAP/COLMAP、Nerfstudio/splatfacto、Qwen-VL、pgvector、Edge Function 等多个技术模块。
2. 普适性高。项目输入数据形态是普通视频或图片，不依赖专用扫描硬件，适合宿舍、房间、桌面等常见生活场景。
3. 热度高。三维内容生成、多模态理解和向量检索均是近年人工智能与空间计算领域的热点方向。
4. 工程难度高。难点不在某一个单点模型，而在于把多个模型、数据库和对象存储稳定接成一个能持续跑通的系统。

# 2    相关工作[[提示6罗列至少三项与之相关的已有技术方案，尽可能是近三年内的技术方案。\]](#_msocom_6) 

1. 基于 COLMAP 的传统 SfM 工作流。该类方案在受控拍摄环境下效果较稳定，但对普通用户随手拍摄的视频容错不足。BrainDance 当前实现保留 COLMAP 作为回退方案，同时引入 GLOMAP 作为主流程中的全局位姿求解器。
2. 基于 Nerfstudio/3DGS 的离线训练工作流。现有开源框架擅长高质量训练，但通常不负责任务编排、对象存储、语义入库和搜索接口。BrainDance 的重点是把训练框架嵌入到完整的业务链路中。
3. 基于向量数据库的 RAG 检索方案。常见 RAG 面向文本或图片，而 BrainDance 将三维模型视为“可语义检索的场景资产”，把描述、标签、物体信息和模型路径共同纳入检索过程。
4. 基于多模态视觉模型的场景理解方案。Qwen-VL 等模型已经具备图像理解能力，但如何将其输出转化为数据库结构并纳入三维处理流程，是本项目的工程重点。

 


# 3    技术方案[[提示7\]](#_msocom_7) 

## 3.1 技术方向[[提示8指出想要使用的技术的所属方向，比如：深度学习、IOT等\]](#_msocom_8) 

项目当前采用的技术方向如下：

- 三维视觉与神经渲染
- 多模态场景理解
- Serverless 云原生后端
- 向量数据库检索
- 异步任务处理

## 3.2 技术选择

结合当前仓库的真实实现，项目技术选择如下：

1. 后端基础设施采用 Supabase。使用 PostgreSQL 承担任务表与资产表，使用 Storage 保存原始视频和输出模型，使用 Realtime 做状态同步。
2. 云端计算节点采用 Python Worker。`worker.py` 负责轮询 `processing_tasks`、下载原始文件、调用具体 Pipeline、同步日志并上传结果。
3. 三维重建采用 FFmpeg + GLOMAP/COLMAP + Nerfstudio/splatfacto。当前已实现“视频抽帧 -> 位姿解算 -> 3DGS 训练 -> 模型上传”的自动化链路。
4. 语义分析采用 Qwen-VL 相关能力。场景分析模块负责生成描述、标签和物体清单，供后续向量化使用。
5. 检索层采用 pgvector。`model_assets` 表中保存 1536 维向量，Edge Function `search-models` 负责意图解析、生成查询向量并调用 `match_model_assets` RPC 完成搜索。
6. 管理与观测端采用独立 Dashboard。该界面基于 Vue 3 + Vite + TypeScript 构建，直接读取 Supabase 中的任务、资产和状态数据，用于任务监控、资产统计和系统运行情况可视化。

当前实现的技术边界需要明确说明：

- 目前已经实现的是“场景级语义检索”，即返回匹配场景及模型路径。
- 目前没有在报告中宣称未落地的端侧推理、移动端 NPU 加速或精确三维物体坐标定位能力。

## 3.3 结果期望[[提示9给出使用该技术的预期结果。注意给出的预期结果应是合理、可行的。\]](#_msocom_9) 

基于当前仓库实现，项目的合理结果期望如下：

1. 建立稳定的云端三维处理闭环，实现从任务提交到模型资产入库的自动化流程。
2. 建立基于场景描述、标签和时间语义的自然语言搜索能力，使三维资产具备可检索性。
3. 通过统一的任务表、资产表和向量检索函数，为后续评测、扩展和产品化保留清晰的数据结构基础。

 


# 4    技术实践[[提示10\]](#_msocom_10) 

## 4.1 使用的开发框架及依赖的库

结合当前仓库，实际使用的框架与依赖主要包括：

- 后端与云服务：Supabase、PostgreSQL、pgvector、Supabase Storage、Supabase Realtime、Deno Edge Functions
- 前端与管理界面：Flutter、Vue 3、Vite、TypeScript、ECharts
- AI 与三维处理：Python 3.10+、PyTorch、Nerfstudio、gsplat、FFmpeg、COLMAP、GLOMAP
- 多模态与检索：Qwen-VL / Qwen-Plus（通过 DashScope 兼容接口调用）、text-embedding-v2

与本报告直接相关的核心实现文件包括：

- `ai_engine/3dgs/src/core/worker.py`
- `ai_engine/3dgs/src/core/pipeline_base.py`
- `ai_engine/3dgs/src/modules/glomap_runner.py`
- `ai_engine/3dgs/src/modules/scene_analyzer.py`
- `ai_engine/3dgs/src/modules/knowledge_base.py`
- `supabase/functions/search-models/index.ts`
- `supabase/migrations/20260118144558_init_schema.sql`

## 4.2 技术实践过程

当前项目已经形成如下技术实践流程：

1. 任务创建。客户端或脚本先把原始视频/图片上传到 Storage，再向 `processing_tasks` 表写入一条 `pending` 任务。
2. 任务消费。Python Worker 轮询任务表，发现待处理任务后将其更新为 `processing`，并开始执行后续流程。
3. 数据下载与本地执行。Worker 从 Storage 下载原始文件到本地工作区，并根据任务类型调用对应 Pipeline。
4. 三维重建。视频任务进入抽帧、位姿解算和 3DGS 训练流程。其中位姿解算优先使用 GLOMAP，失败时回退至 COLMAP Mapper，提高系统可用性。
5. 语义分析。Pipeline 调用场景分析模块，对图像生成描述、标签、物体清单和质量信息。
6. 向量入库。`KnowledgeBase` 将描述、标签和主体物体构造成加权文本，调用 Embedding 接口生成向量，并把向量与元数据写入 `model_assets`。
7. 结果回传。模型文件上传回 Storage，任务日志与状态实时同步到数据库。
8. 语义搜索。Edge Function `search-models` 接收自然语言查询，先做意图解析，再生成查询向量，最后调用 `match_model_assets` RPC 返回匹配场景。
9. 状态观测。独立 Dashboard 通过 Supabase 查询与实时订阅机制展示任务队列、资产变化和节点状态，为系统调试、运行观测和结果展示提供可视化支撑。

这一实践过程说明，BrainDance 当前已经具备“任务调度 - 三维处理 - 语义入库 - 检索返回 - 状态观测”的完整云端原型链路。




# 5    结果验证[[提示11\]](#_msocom_11) 

当前仓库中已有明确测试记录的，主要是语义搜索接口与数据库检索链路。

1. 根据 `docs/03-API参考/API测试报告.md`，`search-models` Edge Function 自动化测试共 11 项，结果为 11 项通过、0 项失败。
2. 已验证的测试内容包括：JSON 解析、日期规范化、空查询拒绝、超长查询拒绝、CORS 预检等关键接口路径。
3. 从现有实测结果看，查询“红色杯子”能够返回标准化响应结构，查询“找一下上周拍的照片”能够正确解析时间范围，说明系统已具备基础自然语言意图理解能力。
4. API 测试报告记录的接口响应时间约为 2-3 秒，当前主要耗时来自意图解析和文本向量生成两次模型调用。

需要如实说明的是，当前仓库尚未沉淀统一、可复现实验集上的以下指标，因此本报告不对这些数据作虚构性填写：

- 视频重建成功率对比数据
- 标准数据集上的几何精度指标
- 检索 Top-k 准确率
- 多用户并发压测结果
- 端侧推理与端云协同时延指标

因此，当前阶段可以确认的结论是：BrainDance 已完成云端三维重建与场景级语义检索的基础闭环验证，证明了“3D 重建 + 多模态语义 + 向量检索”这一技术组合在工程上具备可落地性。
