# **技术研究报告**

# 1    问题聚焦

## 1.1 问题描述

BrainDance（流光·记）聚焦解决的核心问题，不是抽象层面的“空间计算愿景”，而是一条真实可运行的三维空间智能处理链路：用户上传视频或图片后，系统如何自动完成三维重建、结果入库、自然语言检索，以及在移动端侧提供可用的本地问答能力。

项目主要解决以下问题：

1. 传统二维影像只能记录平面画面，缺乏空间结构，无法作为可检索的三维记忆资产长期保存与复用。
2. 视频到三维模型的工程链路长、失败点多，普通输入数据容易在抽帧、位姿解算、训练或上传环节中断，导致系统不可用。
3. 现有三维模型通常只有几何表达，没有语义入口，用户无法通过“宿舍”“红色杯子”“上周拍的照片”等自然语言进行检索。
4. 即便已有云端检索能力，移动端在弱网、离线或高隐私场景下仍缺乏稳定的本地问答能力；直接依赖云端大模型 API 会带来成本、时延和隐私边界问题。
5. 传统“搜索接口”只能返回候选结果列表，难以支撑多轮追问、预览确认、资产批量整理和时间对比等更复杂的空间记忆交互，需要一个可解释、受约束且可流式反馈的 Agent 编排层。

## 1.2 问题抽象

结合项目方案，可将项目问题抽象为以下技术问题：

1. 如何构建一条面向普通视频/图片输入的云端三维重建流水线，使其自动完成抽帧、位姿解算、3DGS 训练、模型上传与任务状态同步。
2. 如何在不额外引入 Redis、独立向量数据库等中间件的情况下，基于 PostgreSQL/Supabase 同时完成任务调度、资产管理和语义检索。
3. 如何利用多模态模型生成场景描述、标签和物体信息，并将这些语义信息转换为向量表示，支撑场景级自然语言搜索。
4. 如何在移动端有限内存和弱算力约束下，把“基于检索证据回答、无证据明确拒答”的能力压缩进可部署的小模型，并建立可重复、可审计的 benchmark 体系。

## 1.3 问题定位

本项目属于“AI 无界”主题下的 AI 影像处理与空间智能交叉方向，具体涉及以下领域：

- 计算机视觉：视频抽帧、图像质量分析、SfM 位姿解算、3D Gaussian Splatting
- 多模态人工智能：图像理解、场景打标、文本向量化、自然语言意图解析
- 端侧大模型工程：知识蒸馏、LoRA / Full SFT、GGUF 量化、本地推理
- 数据库与云计算：Serverless 架构、对象存储、实时订阅、向量检索
- 软件工程：异步任务编排、日志同步、模块化 Pipeline 设计

## 1.4 问题评估

1. 技术性强。项目实际涉及 FFmpeg、GLOMAP/COLMAP、Nerfstudio/splatfacto、Qwen-VL、pgvector、Edge Function 等多个技术模块。
2. 普适性高。项目输入数据形态是普通视频或图片，不依赖专用扫描硬件，适合宿舍、房间、桌面等常见生活场景。
3. 热度高。三维内容生成、多模态理解和向量检索均是近年人工智能与空间计算领域的热点方向。
4. 工程难度高。难点不在某一个单点模型，而在于把多个模型、数据库、对象存储与端侧量化模型稳定接成一个能持续跑通、可验证、可演进的系统。

# 2    相关工作

1. [2302.04264] Nerfstudio: A Modular Framework for Neural Radiance Field Development。该工作提供了模块化的神经辐射场研发框架，并在工程上支持训练、渲染、评估和管线扩展。项目的视频 3DGS 训练流程以其 `splatfacto` 管线为基础，参考了其成熟的实验组织方式与训练框架。
2. [2403.17888] 2D Gaussian Splatting for Geometrically Accurate Radiance Fields。该工作在 Gaussian 表达中进一步强调几何准确性，通过二维高斯表示增强表面约束与渲染一致性。对于需要兼顾视觉效果和几何结构的三维重建任务，这一路线具有较强参考价值。
3. [2504.20378] Sparse2DGS: Geometry-Prioritized Gaussian Splatting for Surface Reconstruction from Sparse Views。该工作面向稀疏视角输入条件下的表面重建问题，重点解决少图像场景中的几何退化和重建不稳定。移动端日常采集往往难以满足高密度、多角度拍摄条件，因此这类方法与项目场景高度相关。
4. [2311.12775] SuGaR: Surface-Aligned Gaussian Splatting for Efficient 3D Mesh Reconstruction and High-Quality Mesh Rendering。该工作将表面对齐约束引入 Gaussian Splatting，进一步支持高质量网格重建与渲染。它说明 Gaussian 表达不仅可以用于新视角合成，也可以向结构化三维表面表达延伸。
5. [2511.10647] Depth Anything 3: Recovering the Visual Space from Any Views。该工作关注从任意视角恢复视觉空间信息，核心能力包括深度估计与视图空间恢复。对于需要增强几何先验、补充三维流水线感知能力的场景，这类方法具有直接参考意义。
6. [2512.10685] Sharp Monocular View Synthesis in Less Than a Second。该工作聚焦单图快速生成高质量视图合成结果，强调极短推理时延下的三维生成能力。对于移动端或轻量输入条件下的三维内容生成，这种单图路线提供了新的实现思路。
7. [2511.16624] SAM 3D: 3Dfy Anything in Images。该工作面向单图条件下的三维物体生成，尝试将二维图像中的目标直接转化为三维对象表达。这类方法为项目在轻量输入条件下扩展单图三维生成能力提供了参考。
8. 基于 COLMAP 的传统 SfM 工作流仍是当前三维重建的重要基础方案，在受控拍摄环境下具有较稳定的位姿估计能力。项目保留 COLMAP 作为回退方案，并在主流程中结合 GLOMAP 以提高普通视频输入下的重建鲁棒性。
9. 基于向量数据库的 RAG 检索方案已广泛应用于文本和图像检索任务，核心思路是将非结构化内容转化为向量后进行语义匹配。项目将这一思路扩展到三维场景资产，将描述、标签、物体信息和模型路径统一纳入检索过程，使三维结果具备自然语言搜索能力。
10. 基于多模态视觉模型和大语言模型的场景理解方案已经具备较强的图像描述、目标识别、意图解析和语义组织能力。项目并非只使用单一的 Qwen-VL 模型，而是结合 Qwen 系列模型构建完整语义链路：在场景分析阶段使用 `qwen3-vl-plus` 生成质量评分、场景描述、标签和物体清单；在部分图像确认场景中使用 `qwen-vl-max` 完成图像分类；在搜索阶段使用 `qwen-turbo` 解析自然语言查询中的目标与时间范围，再通过 `text-embedding-v2` 生成向量并接入 pgvector 检索，从而形成从视觉理解到语义检索的完整闭环。
11. 参数高效微调（PEFT）、GGUF 量化和端侧推理运行时的发展，使“小模型 + 本地推理”成为可行路线。但多数工作更关注通用聊天、代码或知识问答，较少面向“基于检索证据回答的空间问答”这一窄而难的业务场景。项目基于 Qwen3 构建定向微调链路，将端侧模型训练目标从“会聊天”收缩为“会基于证据短答、会拒答、会处理 partial coverage”，使小模型更贴近真实产品任务。
12. 在评测方法上，传统 benchmark 往往假定上游数据静止不变，而本项目的真实场景数据会持续写入 Supabase，导致 `recent_*` 问题天然存在漂移风险。为避免把 retrieval 漂移误判成模型能力波动，项目引入 retrieval snapshot 冻结复现机制，把 live 口径与 frozen 口径并行保留，这一点在工程研究层面具有明显的方法论价值。

 


# 3    技术方案

## 3.1 技术方向

项目当前采用的技术方向如下：

- 三维视觉与神经渲染
- 多模态场景理解
- 端侧大模型蒸馏与量化部署
- Serverless 云原生后端
- 向量数据库检索
- 异步任务处理
- 可复现 benchmark 与部署审计

## 3.2 技术选择

结合项目的实际实现，技术选择如下：

1. 移动端采用 Flutter 构建，结合 Riverpod、相机采集、素材选择和 WebView 模型浏览能力，完成素材采集、任务提交、状态查看和结果回访等核心交互流程。
2. 后端基础设施采用 Supabase。使用 PostgreSQL 承担任务表、资产表和空间记忆相关数据表，使用 Storage 保存原始视频、图片和输出模型，使用 Realtime 做状态同步，并结合 Auth、RLS 和 Edge Functions 形成完整的端云协同支撑能力。
3. 云端计算节点采用 Python Worker。`worker.py` 负责轮询 `processing_tasks`、下载原始文件、调用具体 Pipeline、同步日志并上传结果。
4. 三维重建主链路采用 FFmpeg + GLOMAP/COLMAP + Nerfstudio/splatfacto，已实现“视频抽帧 -> 位姿解算 -> 3DGS 训练 -> 模型上传”的自动化处理流程。同时，系统还接入了 `single_image_sam3d`、`single_image_sharp`、`da3_feed_forward_3dgs`、`da3_sugar`、`da3_2dgs`、`sparse2dgs` 等多种任务流水线，以适配不同输入条件和重建需求。
5. 多模态理解与语义分析采用 Qwen 系列模型。场景分析模块默认使用 `qwen3-vl-plus` 生成描述、标签、物体清单和质量评分，部分图像确认流程使用 `qwen-vl-max`，相关结果统一写入资产库，供后续向量化和检索使用。
6. 语义检索链路采用 `qwen-turbo`、`text-embedding-v2` 与 pgvector。Edge Function `search-models` 负责自然语言意图解析、查询向量生成和向量检索调用，使三维场景资产具备自然语言搜索能力。
7. 在线 Agent 编排链路采用 Supabase Edge Functions + LangChain TS。当前正式入口为 `agent-recall`，实验入口为 `spatial-search-agent`，两者共享 `_shared/agent-core/spatialAgent.ts`，并统一输出 `answer / evidence / actions / follow_up / session_state` 等结构化字段。
8. 时间对比与记忆整理能力以 Agent 工具链形式并入在线链路。`time-compare-agent` 负责双时间窗口对比，`memoryTools.ts` 负责专题归档、线程归组、相关模型查找、创作上下文与弱图谱摘要。
9. 管理与观测端采用独立 Dashboard。该界面基于 Vue 3 + Vite + TypeScript 构建，结合 ECharts 展示任务、资产、存储和节点状态，用于任务监控、资产统计和系统运行情况可视化。
10. 端侧本地问答链路采用 `Qwen3-1.7B / 0.6B` 作为小模型基座，通过 Teacher-Student 数据合成、LoRA / Full SFT、merge、GGUF 量化和 `llamadart` 等本地运行时完成部署探索。根据 [Qwen3-本地问答模型综合横评总览-2026-03-24.md](/home/ltx/projects/BrainDance/docs/04-本地问答与微调/Qwen3-本地问答模型综合横评总览-2026-03-24.md) 的现有结论，`1.7B LoRA` 是稳定质量基线，`1.7B Q5_K_M + imatrix GGUF` 是当前部署主线首选，`0.6B LoRA` 作为资源受限机型的轻量备选。
11. 模型评测链路采用脚本化 benchmark 体系。除 strict benchmark 外，还补充未见数据 OOD 基准、空间关系 hardcases、deployment eval 与 retrieval snapshot 冻结复跑，用于定位“模型回答问题”与“上游 retrieval 漂移问题”。根据 [Qwen3-评测快照复现说明-2026-03-24.md](/home/ltx/projects/BrainDance/docs/04-本地问答与微调/Qwen3-评测快照复现说明-2026-03-24.md)，当前评测已明确区分 `live` 与 `frozen` 两种口径。



## 3.3 结果期望

基于项目现有实现，项目的合理结果期望如下：

1. 建立稳定的云端三维处理闭环，实现从任务提交到模型资产入库的自动化流程。
2. 建立基于场景描述、标签和时间语义的自然语言搜索能力，使三维资产具备可检索性。
3. 建立端侧本地问答能力，使移动端在弱网或高隐私场景下也能完成基础空间问答与安全拒答。
4. 通过统一的任务表、资产表、benchmark 日志和 snapshot 机制，为后续评测、扩展和产品化保留清晰的数据与审计基础。

 


# 4    技术实践

## 4.1 使用的开发框架及依赖的库

结合项目实际，使用的框架与依赖主要包括：

- 系统与运行环境：Ubuntu 22.04.5 LTS、CUDA 12.8、NVIDIA Driver 570.211.01、Python 3.10.12，AI Engine 在双 NVIDIA L20 GPU 环境下完成训练与推理任务。
- 后端与云服务：Supabase、PostgreSQL、pgvector、Supabase Storage、Supabase Realtime、Auth、RLS、Deno Edge Functions、Docker、Supabase CLI。
- 前端与管理界面：Flutter、flutter_riverpod、camera、image_picker、webview_flutter、supabase_flutter、Vue 3、Vite、TypeScript、ECharts、Element Plus。
- AI 与三维重建：PyTorch、Nerfstudio、gsplat、FFmpeg、COLMAP、GLOMAP、OpenCV、Open3D、pycolmap、xformers、rawpy、pymeshlab、point-cloud-utils。
- 多模态与检索：qwen3-vl-plus、qwen-vl-max、qwen-turbo（均通过 DashScope 兼容接口调用）、text-embedding-v2、OpenAI 兼容 SDK、DashScope SDK。
- 端侧微调与量化：Transformers、PEFT、GGUF 相关转换链路、本地量化脚本、`llamadart` 运行时集成路线。
- 论文复现与扩展流水线相关依赖：SuGaR、Sparse2DGS、2D Gaussian Splatting、Depth Anything 3、SHARP、SAM 3D Objects，以及对应的本地源码子模块与可编辑安装策略。

其中，AI Engine 当前实际环境中的 Python 依赖规模较大，总量超过 500 个包；报告中仅列出与系统主链路直接相关的核心框架和关键依赖。


## 4.2 技术实践过程

项目已经形成如下技术实践流程：

1. 任务创建。客户端或脚本先把原始视频/图片上传到 Storage，再向 `processing_tasks` 表写入一条 `pending` 任务。
2. 任务消费。Python Worker 轮询任务表，发现待处理任务后将其更新为 `processing`，并开始执行后续流程。
3. 数据下载与本地执行。Worker 从 Storage 下载原始文件到本地工作区，并根据任务类型调用对应 Pipeline。
4. 三维重建。视频任务进入抽帧、位姿解算和 3DGS 训练流程。其中位姿解算优先使用 GLOMAP，失败时回退至 COLMAP Mapper，提高系统可用性。
5. 语义分析。Pipeline 调用场景分析模块，对图像生成描述、标签、物体清单和质量信息。
6. 向量入库。`KnowledgeBase` 将描述、标签和主体物体构造成加权文本，调用 Embedding 接口生成向量，并把向量与元数据写入 `model_assets`。
7. 结果回传。模型文件上传回 Storage，任务日志与状态实时同步到数据库。
8. 语义搜索。Edge Function `search-models` 接收自然语言查询，先做意图解析，再生成查询向量，最后调用 `match_model_assets` RPC 返回匹配场景。
9. Agent 编排。`agent-recall` 将检索升级为统一多模式入口，请求可携带 `selectedModelIds`、`executionMode`、`sessionState`、`conversationSummary` 等上下文，系统根据问题在 `spatial_search`、`asset_metadata`、`time_compare`、`creative`、`memory_graph` 之间路由。
10. 记忆专题与时间对比。共享 Agent Core 在 `memoryTools.ts` 中调用相关工具，并依赖 `place_id`、`memory_thread_id`、`related_model_links`、`memory_collections` 等新增数据结构，实现专题归档、线程归组、相关模型推荐和双时间窗口差异总结。
11. 前端消费。Flutter Recall 页通过 `agent_recall_service.dart` 同时支持普通调用与 `SSE / NDJSON` 流式调用，把 `status / tool_call / tool_result / done` 展示为过程时间线，并自动回传 `session_state / conversation_summary` 支持多轮续聊。
12. 状态观测。独立 Dashboard 通过 Supabase 查询与实时订阅机制展示任务队列、资产变化和节点状态，为系统调试、运行观测和结果展示提供可视化支撑。
13. 端侧本地问答训练。团队基于真实场景任务特征合成训练样本，使用 `Qwen3` 执行 LoRA / Full SFT 对照实验，并形成 `Part16-Part30` 的持续记录。
14. 候选模型部署。通过 merge、GGUF 量化、imatrix 校准与 deployment eval，对 `1.7B LoRA`、`1.7B merged`、`1.7B Q5_K_M + imatrix`、`0.6B LoRA` 等候选进行综合比较。
15. 冻结复现评测。对 benchmark 的 retrieval 结果先导出 snapshot，再在 frozen 口径下复跑多版本模型，用于排除数据库实时变化对评测结论的干扰。

这一实践过程说明，BrainDance 已经具备“任务调度 - 三维处理 - 语义入库 - 检索返回 - 端侧问答 - 状态观测”的完整技术原型链路。
