# 项目概述

## 项目背景

在⼈类记录⽣活的演进史中，从⽂字、绘画到照⽚、视频，我们始终受限于“⼆维介质”的表达框架。然⽽，⼈ 类的记忆本⾝是三维的、充满空间感与⽅位感的。传统⼆维影像只能记录单⼀的切⾯画⾯，⽆法保留物体之间 的真实空间关系，更⽆法在事后提供⾃由交互与视⾓重游的能⼒。

**BrainDance（流光·记）** 应运⽽⽣。作为⼀款⾯向移动端的“可检索三维记忆应⽤”，它致⼒于打破⼆维介质的 物理局限，将现实空间转化为**可浏览、可检索、可回看视⾓的三维数字资产**。

BrainDance 被打造成⼀个强⼤的**“可检索三维记忆库”**。其核⼼突破⽅向聚焦于四个维度：

1\.**移动端低成本扫描：**摆脱昂贵的专业设备依赖。

2\.**空间语义检索与 Agent Recall：**多模态 LLM + RAG + LangChain Agent，让空间内的物品、时间差异与资产操作都可以通过⾃然语⾔被“搜出来、整理掉、继续问”。

3\.**时光剥离（Time Peeling）：**记录同⼀空间在不同时间维度的变化。

4\.**端云协同计算：**平衡移动端算⼒瓶颈与⾼质量三维重建需求。

BrainDance 不仅是⼀个⼯具，更是⾯向未来的“记忆留存舱、空间消失记录仪、个 ⼈数字海马体”。

## 项目定位

### 应用场景

BrainDance 颠覆了“拍⼀段视频”的传统记录⽅式，它能够把⼀个流动的场景固化为可再次进⼊、可深度交互的 三维记忆。其核⼼应⽤场景包括︓

1\.**个⼈专属空间留存：**记录即将搬离的童年卧室、充满回忆的⼤学宿舍，或是精⼼布置的婚房。在未来任 何时刻，⽤户都能以第⼀⼈称视⾓在数字空间中漫游，重温当时的感动。

2\.**城市记忆与建筑档案：**为⾯临拆迁的⽼街区、历史建筑或正在改造的物理空间进⾏“数字化存档”。不仅 保留外观，更保留空间的纵深与肌理。

3\.**可语义检索的个⼈资产库：**例如，⽤户可以通过搜索“桌⼦上的红⾊马克杯”，应⽤直接在三维模型中⾼ 亮并跳转⾄该物品所在的视⾓位置，实现真正的“空间档案管理”。

4\.**XR（扩展现实）原⽣内容⽣产：**为未来的空间计算设备（如 Apple Vision Pro、Meta Quest）提供直接 可⽤的、源⾃真实⽣活的三维原⽣内容。

### 目标人群

项⽬采⽤分层⽤户策略，满⾜不同深度的使⽤需求：

1\.**⼤众记录者（核⼼⽤户）：**希望以极低成本（仅需⼀部智能⼿机）、极低门槛记录⽣活空间变化的普通 ⼤众。

2\.**⽂化/城市记录者（专业⽤户）：**需要对城市变迁、展览现场、⽂化遗产进⾏⾼保真三维留存的记者、摄 影师或档案管理⼈员。

3\.**空间内容创作者（⽣产⽤户）：**需要快速获取真实世界 3D 扫描资产，⽤于游戏开发、影视预演或虚拟 现实创作的开发者。

4\.**（愿景延展）特殊照护与家庭陪伴：**为阿尔茨海默症患者提供熟悉的“数字记忆空间”进⾏怀旧疗法，或 为异地家庭提供极具沉浸感的“数字回乡”体验。虽作为未来延展⽅向，但这是⽀撑项⽬长期社会价值的重要基⽯。

## 项目方案

项⽬创新性地采⽤了 “Flutter 移动端 + Supabase BaaS + Python Worker” 的端云协同架构，实现了从前端 采集到后端 AI 重建的⾼效闭环。

**前端交互层 (Flutter 移动端)：**

作为跨平台的移动⼊⼝，负责提供流畅的⽤户界⾯。

核⼼模块包括︓⽤户账户管理（登录/注册）、数据采集录制（引导⽤户拍摄符合重建要求的视频/ 图⽚）、任务⽣成⼊⼝，以及基于内嵌 WebView 的⾼性能三维模型查看器。

**云端调度层 (Supabase BaaS)：**

作为整个系统的中枢神经，Supabase 提供了强⼤的后端即服务。

Auth 负责安全鉴权；Object Storage ⽤于暂存⽤户上传的原始影像和⽣成的 3D 模型；PostgreSQL 数据库（任务表/模型表）记录任务状态与元数据。

利⽤ Realtime 与 Edge Function 实现状态的实时推送与轻量级逻辑处理，确保前端能即时感知云端重建进度。近期又新增了 `agent-recall` 统一入口、`spatial-search-agent` 实验入口、`time-compare-agent` 专用时间对比能力，以及共享 Agent Core `spatialAgent.ts`，使 Recall 页不再只是调用单一 `search-models` 接口，而是能够进行多模式查询、多轮续聊和流式过程展示。

**AI 计算层 (Python Worker)：**

部署在拥有强⼤ GPU 算⼒的云端或边缘节点，通过异步消费 Supabase 任务表中的指令进⾏繁重 的 AI 计算。

集成了多条前沿的 AI 三维⽣成流⽔线，且不再局限于单一视频建模路线，而是基于 `task_type` 形成了“**视频重建 + 单图生成 + 少图重建 + 快慢双链 + 论文复现组合链路**”的多 Pipeline 体系，包括：

**video\_3dgs：**基于视频的默认 3D Gaussian Splatting（三维高斯泼溅）高质量重建主线，可结合 GLOMAP / COLMAP / DA3 等不同前端位姿或深度信息组织方式。

**video\_dual\_chain：**面向移动端体验的快慢双链任务编排机制，先给出可快速预览的结果，再并行或顺序进入更高质量的慢链重建流程。该链路直接对应比赛要求中强调的“轻量化操作、场景化响应、即时性服务”：用户只需提交一次视频任务，系统就会先返回可浏览、可确认采集范围的预览资产，再继续自动进入慢链精修，避免移动端用户长时间无反馈地等待完整高质量 3DGS 训练结束。

**da3\_feed\_forward\_3dgs：**基于 Depth Anything 3 的前馈式 3DGS 快速生成链路，强调极速出结果与预览友好性。

**da3\_sugar（或 da3+sugar）：**Depth Anything 3 与 SuGaR 的组合型高质量重建链路，适合质量优先、可接受更长耗时的场景。

**da3\_2dgs（或 da3+2dgs）：**Depth Anything 3 与 2DGS 的组合路线，面向少图或中短视频条件下更强调几何质量和替代型表示的重建需求。

**sparse2dgs：**针对极稀疏视角或少量图片输入的 Sparse2DGS 路线，用于低视角数量条件下的三维生成。

**single\_image\_sam3d：**基于 SAM 3D Objects 的单图对象级三维生成，适合单物体、单主体场景的快速 3D 化。

**single\_image\_sharp：**基于 Apple SHARP 的单图快速生成链路，强调单图条件下的极速三维预览能力。

整体上，Worker 已从“只跑一条 3DGS 流程”的原型阶段，演进为可按任务类型动态分发、按输入形态自适应处理、按质量与时延目标切换策略的多流水线三维计算平台。

计算完成后，⾃动将 3D 模型⽂件、预览缩略图和空间元数据写回 Supabase 存储池与数据库，完 成闭环

**端侧智能层 (On-Device Local QA)：**

除云端多模态检索外，项目新增了面向移动端与弱网场景的本地问答能力。该能力基于 `Qwen3-1.7B / 0.6B`
的小模型路线，围绕“**知识蒸馏 + LoRA SFT + GGUF 量化 + 端侧部署**”构建了完整工程流水线。

该链路的目标不是把用户事实写进参数，而是训练模型“**如何基于检索证据稳定作答、在无证据时明确拒答**”。
当前已完成：

1\. Teacher-Student 数据合成与定向蒸馏；

2\. `Qwen3-1.7B` 与 `Qwen3-0.6B` 的 LoRA / Full SFT 对比实验；

3\. `Q5_K_M + imatrix` 量化压缩与候选部署验证；

4\. 本地 benchmark、严格无泄漏评测、OOD 新数据评测与 retrieval snapshot 冻结复现机制。

## 项目目标

为了确保项⽬的稳步推进，当前阶段设定了以下七个核⼼⾥程碑：

1\.**实现语义级资产管理：**不仅让⽤户能够在“我的记忆”中以画廊形式浏览 3D 资产，更要跑通基于多模态 LLM 和空间理解的⾃然语⾔语义搜索功能。

2\.**打通端云算⼒闭环：**实现“移动端上传视频/图⽚ -\> 云端⽣成异步任务 -\> Worker 节点执⾏ 3D 重建 -\> 结果回传展⽰”的完整数据流。

3\.**构建应⽤基础⾻架：**完成跨平台的 Flutter 移动端三维记忆应⽤基础架构设计与 UI 搭建。

4\.**攻克移动端 3D 渲染与交互：**实现基于移动端 WebView 的⾼性能模型加载，并⽀持“定位视⾓跳转”（即 点击搜索结果，摄像机⾃动平滑推拉⾄对应三维坐标）。同时，项目以 OPPO Find X8 等主流移动端设备为性能标定对象，持续优化本地代理、模型加载与渲染链路，目标是在主流安卓设备上实现大于等于 60fps 的实时渲染体验。

5\.**攻克 3DGS 边缘质量与前景纯净度问题：**针对单物体链路，项目并非简单依赖单一分割模型，而是实现了“Qwen-VL 中心主体理解 + YOLOWorld 检测 + SAM 精细分割 + 连通域保留最大主体 + 实心度校验 + 长宽比筛选 + 边缘腐蚀 + 透明 PNG 导出”的高鲁棒性前景提取流程，用于尽可能消除背景粘连、阴影干扰和边缘杂色。针对真实场景链路，项目通过引入 Depth Anything 3 替代传统单一路径位姿前端，先生成更稳定的深度、点云与高精度相机位姿，再接入 Nerfstudio `splatfacto` 训练，并对 `cull-alpha-thresh`、`stop-split-at`、`warmup-length`、`refine-every`、`reset-alpha-every`、`densify-grad-thresh`、`split-screen-size` 等关键参数进行针对性微调；同时结合自适应 collider 分析与点云后处理裁剪，显著减少场景边缘凌乱漂浮的高斯椭球，提高模型轮廓干净度与整体观感。

6\.**构建端侧本地问答能力：**完成 `Qwen3-1.7B / 0.6B` 的定向微调、量化与候选部署验证，使移动端在弱网或隐私敏感场景下仍具备基础空间问答能力。

7\.**建立可复现评测体系：**补齐 strict benchmark、未见数据 OOD benchmark、空间高难基准与 retrieval snapshot 固化机制，确保模型迭代具备可追溯、可对比、可审计的工程标准。

## 项目价值

**产品与⽤户价值：**将⼤众习以为常的“⼆维相册”跨时代地升级为“空间记忆资产库”。它赋予了记忆以物理 维度，让“记忆保存”从平⾯的被动观看，提升为⽴体的、可探索的交互式空间漫游，极⼤地丰富了情感 留存的载体。

**⾏业与⽣态价值：**⼤幅降低了 3D 空间内容的⽣产门槛。在即将到来的空间计算（Spatial Computing） 时代，BrainDance 有望成为重要的原⽣空间数据采集⼊⼝，为 XR 软硬件⽣态源源不断地输送来⾃真实 世界的 UGC（⽤户⽣成内容）三维资产。

**⼯程与学术价值：**学术价值上，BrainDance 实现了最新学术论⽂的落地。在⼯程实现上，BrainDance 不仅将移动端设备采集、现代 BaaS 平台调度、重度 AI 渲染重建以及前沿的 3D 语义检索技术串联为统⼀系统，还进一步完成了面向移动端的本地问答模型蒸馏、轻量化量化与严格评测闭环，形成“**重建 + 检索 + 端侧智能**”三位一体的工程范式。

# 开发计划

## 最终呈现形式

BrainDance 最终将以 “⾼可⽤移动端 App + 强算⼒云端处理系统” 的端云协同形态呈现。为了降低⽤户的学习 成本并提供清晰的操作流，移动端精⼼设计了四⼤主导航结构，将复杂的 3D 扫描与检索过程极简化：

1\.**Recall（回忆）：**⽤户的核⼼资产画廊。以瀑布流或时间轴形式展⽰已⽣成的三维空间资产，并提供⾃ 然语⾔的语义搜索⼊⼝。

2\.**Record（录制）：**数据采集核⼼。引导⽤户按规范调⽤物理摄像头拍摄视频或采集图像，确保符合后端 3DGS 算法的重建要求。

3\.**Generate（⽣成）：**任务调度中⼼。⽤户可在此查看“上传-排队-重建-下发”的全链路异步任务进度。

4\.**Settings（设置）：**系统与账户管理。包含个性化主题、语⾔切换及 Supabase 会话状态管理。

在主导航框架下，系统衍⽣出包括 Login（登录注册）、VideoSubmit（视频元数据完善与提交）、 WebGLViewer（⾼性能三维模型渲染器）等关键⼆级页⾯。同时，Recall 页的空间检索能力正在向“**云端 RAG + 端侧本地问答协同**”演进：云端负责高质量检索与复杂推理，端侧负责低延迟、隐私友好的基础问答和兜底交互。

## 运行环境

BrainDance 并不是“单一前后端 + 单一依赖”的传统应用，而是一个由**移动端、BaaS 后端、边缘函数、GPU Worker、Web 3D 查看器、实验性端侧问答链路**共同组成的异构系统。各模块运行时、依赖管理方式、硬件要求和部署位置均不相同。

从当前仓库结构与依赖文件看，项目至少包含以下几套彼此独立但相互协作的环境：

| 层级 | 目录/模块 | 主要职责 | 运行时/语言 | 依赖管理 |
|------|-----------|----------|-------------|----------|
| 移动端客户端 | `app/` | 登录、录制、上传、模型浏览、检索入口 | Flutter / Dart | `pubspec.yaml` |
| 云端基础设施 | `supabase/` | 数据库、对象存储、认证、Realtime、Edge Functions | Supabase Local / PostgreSQL / Deno | Supabase CLI、Docker、函数本地 `.env` |
| AI 重建 Worker | `ai_engine/3dgs/` | 任务轮询、视频重建、单图生成、资产回写 | Python 3.10 + CUDA + PyTorch | Conda + `requirements.txt` + 子模块源码安装 |
| Web 运维看板 | `dashboard/` | 查看任务、资产和运行状态 | Vue 3 / TypeScript / Vite | `package.json` |
| 3D 查看器工具链 | `3dgs_viewer/`、`app/assets/webgl*` | 3DGS 模型渲染、调试和展示 | Vue 3 / Three.js / Vite / WebGL | `package.json` |
| 本地问答实验链路 | `ai_engine/finetune_qwen3/` | 微调、量化、评测与本地问答验证 | Python 3.10+ | 独立脚本与实验依赖 |

将运行环境拆分为如下六部分：

### 1. 移动端运行环境（正式用户入口）

移动端是项目的主要交互入口，当前以 Android 真机为核心目标平台，负责账号登录、视频采集、上传任务、查看 3D 资产、发起语义检索以及承载端侧问答入口。代码位于 `app/`，依赖定义在 `app/pubspec.yaml`。

其实际环境要求如下：

| 项目 | 当前要求 |
|------|----------|
| 操作系统 | Android  |
| 开发框架 | Flutter |
| Dart SDK | `^3.10.7` |
| 关键依赖 | `supabase_flutter`、`camera`、`webview_flutter`、`flutter_riverpod`、`dio`、`llamadart` |
| 本地配置 | `app/.env`（由 `app/.env.example` 派生） |

其中，`camera` 负责移动端素材采集，`supabase_flutter` 负责连接 Supabase 的鉴权、数据与对象存储服务，`webview_flutter` 负责承载内嵌 3D 查看器，`dio` 负责 Agent 流式请求与事件解析，`llamadart` 则对应端侧本地问答能力。这意味着移动端本身既不是纯 UI App，也不是简单调用 REST API 的壳，而是一个承担采集、上传、浏览、本地 AI 与在线 Agent 交互职责的复合客户端。

### 2. 后端运行环境（Supabase BaaS + Edge Functions）

本项目没有传统意义上的自建 Java / Go / Node 主业务后端，而是以 Supabase 作为后端基础设施。实际运行环境由 PostgreSQL、Storage、Auth、Realtime、Edge Functions 共同构成，本地开发依赖 `supabase/` 目录下的配置与迁移文件。

| 项目 | 当前要求 |
|------|----------|
| 基础设施 | Supabase Local / Cloud |
| 本地运行前提 | Docker、Supabase CLI |
| 数据库 | PostgreSQL 15+ |
| 向量能力 | `pgvector` |
| 边缘函数运行时 | Deno |
| 关键函数 | `supabase/functions/search-models`、`supabase/functions/agent-recall`、`supabase/functions/spatial-search-agent`、`supabase/functions/time-compare-agent` |
| 关键环境变量 | `SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`、`DASHSCOPE_API_KEY` 等 |

该层的复杂性主要体现在四点：第一，数据库不只存普通业务数据，还承担 `processing_tasks` 任务队列、`model_assets` 资产管理、向量检索、记忆专题与弱关系组织等职责；第二，Storage 直接承载原始视频、缩略图、PLY/SPLAT 等模型文件；第三，`search-models` 边缘函数需要在 Deno 环境中调用外部 Embedding 服务并执行向量检索；第四，`agent-recall` 需要在 Edge Runtime 中完成多模式路由、工具调用、结构化输出以及 `SSE / NDJSON` 流式事件发送。

### 3. AI Worker 与 3DGS 主流水线运行环境（核心重计算环境）

`ai_engine/3dgs/` 是项目中对环境要求最高、也是最复杂的部分。该模块负责轮询数据库任务、执行抽帧、位姿估计、3DGS 训练、单图 3D 重建、AI 场景理解、结果上传与日志回写。根据仓库内 `ai_engine/3dgs/ENVIRONMENT.md`、`README.md`、`requirements.txt` 以及子模块结构，当前这部分必须视为**独立 GPU 计算环境**进行维护。

| 项目 | 当前要求 |
|------|----------|
| 操作系统 | Ubuntu 22.04.5 LTS / Windows 11 WSL2（推荐 Linux/WSL GPU 环境） |
| Python | 3.10.x |
| 环境管理 | Conda |
| 指定环境名 | `Braindance` |
| GPU / CUDA | NVIDIA GPU，CUDA 12.x 为当前主路径 |
| 深度学习框架 | PyTorch 2.10.0+cu128 |
| 系统级工具 | FFmpeg、COLMAP、GLOMAP、Nerfstudio CLI |
| Python 依赖入口 | `ai_engine/3dgs/requirements.txt` |
| 实际补充依赖 | `ai_engine/3dgs/src/libs/*` 子模块源码与可编辑安装 |

该环境并非单纯 `pip install -r requirements.txt` 即可完成，原因在于：

1. `requirements.txt` 只是最小运行入口，真实链路还依赖 `nerfstudio`、`sam-3d-objects`、SHARP、Depth-Anything-3、SuGaR、Sparse2DGS 等子模块或源码安装组件。
2. 多个依赖带有 CUDA、C++ 扩展或显卡架构约束，如 `torch`、`torchvision`、`gsplat`、`xformers`、`pycolmap`、`open3d` 等，不同机器上往往需要重新编译或匹配 wheel。
3. 系统工具链中 `COLMAP`、`GLOMAP`、GPU 版 `FFmpeg` 均属于与 Python 环境并列的外部依赖，缺失任一项都会导致视频重建流程无法闭环。


### 4. Web 端运维看板与 3D 查看器环境

项目中至少存在两类 Node/Web 前端环境，其依赖亦不相同：

| 模块 | 目录 | 主要技术 | 说明 |
|------|------|----------|------|
| 运维看板 | `dashboard/` | Vue 3、TypeScript、Vite、Element Plus、ECharts、`@supabase/supabase-js` | 用于观察任务、资产与系统状态 |
| 3D 查看器 | `3dgs_viewer/my-3dgs-viewer/` 等 | Vue 3、Three.js、`@mkkellogg/gaussian-splats-3d`、Vite | 用于 3DGS 模型渲染与调试 |


### 5. 本地AI问答微调与评测环境

项目目前包含 `ai_engine/finetune_qwen3/` 链路，用于基于qwen3 1.7b/0.6b本地问答模型的蒸馏、LoRA 微调、量化、基准评测与部署验证。是项目技术路线中的重要组成部分，相关文档在 `docs/04-本地问答与微调/` 下已形成大量实验记录。



## 验收标准

为保障应用达到交付与展示要求，设定以下六项核心验收标准，涵盖产品体验与工程健壮性：

**1.基础流程闭环：**用户能够顺畅完成注册/登录，并成功进入 Recall/Record/Generate/Settings 四主导航结构。

**2.资产管理可视化：**用户能够在 Recall 页面正确拉取并以缩略图形式浏览已拥有的所有 3D 模型资产。

**3.语义检索可用性：**系统能够准确解析用户的自然语言查询条件，查询空间语义数据库，并高亮返回包含目标物品的 3D 模型。

**4.本地AI小模型微调后问答可用性：**端侧问答链路在命中检索证据时能够稳定输出简洁答案，在证据不足时明确拒答；部署候选模型具备经严格集、OOD 集与小样本部署验证后的可用性。

**5. 3D 交互与跳转：**用户点击模型或搜索结果后，移动端 WebView 能够无严重卡顿地加载 3D 模型，并支持“定位视角跳转”（即摄像机自动平滑推拉至搜索物品所在的精确三维坐标）。

**6.端云协同可靠性：**移动端上传大文件后，后端 Worker 能够稳定完成异步任务的处理（视频位姿解算 -\> 3DGS 训练），并将最终生成的模型文件、预览图准确写回对象存储（Storage）与资产表（model\_assets）。

**7.快慢双链时效性：**默认视频生成任务能够以 `video_dual_chain` 方式运行，先交付快链预览结果，再自动接续慢链高质量重建；前端对同一 `scene_id` 仅展示一张卡片，并在慢链完成后自动覆盖更新，避免重复资产干扰用户判断。

**8.评测可复现性：**本地问答 benchmark 支持 retrieval snapshot 冻结复现，能够区分“检索漂移”与“模型回答退化”两类问题。

**9.容错与异常处理：**对于因素材质量极差、显存溢出、量化部署失败或检索链路漂移导致的异常，系统能够截获错误，保留关键日志，并将数据库状态正确标记为 failed，同时在前端给予用户友好的重试提示。

## 关键问题

在推进从“二维影像记录”向“三维空间计算”演进的过程中，本项目面临着多项现实的工程壁垒。本项目在代码层面采取了一系列务实的工程化应对策略，核心痛点与解决/规避方案总结如下：

**1. 移动端采集质量波动与位姿解算鲁棒性**

**问题描述：**移动端用户拍摄的视频在抽帧后，常存在严重的运动模糊、抖动或局部纹理缺失，这会直接导致后端 SFM（运动恢复结构）位姿解算失败或最终 3DGS 模型质量崩塌。

**工程对策：**后端的处理 Pipeline 中引入了智能画质过滤机制。当前采用 OpenCV 计算拉普拉斯方差结合分位数阈值，对模糊帧进行智能剔除；若剔除后剩余帧数仍过于庞大，则进一步执行均匀降采样，以平衡计算量与重建质量。

**2. 重建耗时与大文件交付格式的平衡**

**问题描述：**高质量的三维训练链路耗时极长，且生成的大文件在移动端弱网环境下的下发与解析面临巨大挑战。特定的轻量化压缩格式（如 .ksplat）在某些极端场景下极易发生 OOM（显存溢出）或转换崩溃，导致整个任务功亏一篑。

**工程对策：**系统在工程上通过动态参数 delivery\_format 支持多格式输出（.ply / .splat / .ksplat）。在典型交付场景下，经过压缩优化后的模型体积可由平均约 200MB 降至约 20MB，显著降低移动端弱网环境下的传输与解析压力，实现秒级下载与加载体验；同时，移动端查看链路配套实现了断点续传与本地缓存机制，避免大模型下载过程中因网络抖动而被迫整包重来。更关键的是，Worker 中实现了自动容错回退机制——若压缩环节失败，系统将自动回退并上传未压缩的原始 .ply 文件，确保任务最终必定可交付，而不至于全盘失败。针对比赛强调的“即时性服务”，项目进一步以 `video_dual_chain` 将“快链先可见、慢链再精修”纳入默认视频任务编排，使用户在高质量重建尚未结束时就能获得第一阶段可视结果，避免现场展示与真实使用中的长时间空窗。

**3. 移动端 3D 查看器的 WebGL 兼容性壁垒**

**问题描述：**移动端内嵌的 WebView 引擎对 HTTPS 证书校验、跨域资源共享（CORS）以及本地文件系统访问存在极其严格的限制，导致直接加载云端 3D 大模型时常被浏览器内核拦截。

**工程对策：**移动端通过在本地动态拉起一个微型 HTTP 服务器（Local Server），结合 /proxy/ 代理策略及本地模型文件缓存，巧妙规避了证书与跨域问题，并显著提升了同一模型的二次打开与渲染速度。

**4. 空间坐标系对齐与视角跳转复杂度**

**问题描述：**实现“搜索物品并自动拉近镜头”的核心在于坐标系的精准转换。后端的 3DGS 坐标系与前端 WebGL（基于 Three.js）渲染引擎所需的矩阵格式存在差异，该环节一旦出错，会导致模型“能正常加载，但相机视角跳转完全错位（飞出边界）”。

**工程对策：**当前实现中，后端在导出锚点坐标时，严格遵循 Three.js 的列主序（Column-Major）矩阵规范，通过 c2w.T.flatten() 进行矩阵转置与展平输出，以确保前后端空间语义坐标的精准对齐。

**5. 前沿 AI 算法接入的工业化架构预留**

**问题描述：**DA3、前馈式极速 3DGS 、SAM 及 SHARP 单图生成 3dgs 均是极具前沿性的技术链路，目前业界尚无统一的工业化流水线标准，若深度耦合会带来极高的重构风险。

**工程对策：**项目中采用了“多 Pipeline 并行接入 + 工厂模式分发”的架构设计。通过 PipelineFactory 统一规范各种算法类的生命周期，大幅降低了技术迭代与算法替换的工程成本。

**6. 端侧小模型的精度、幻觉与内存约束**

**问题描述：**移动端本地问答能力必须在有限内存、较弱算力与不稳定网络条件下运行。若直接使用云端大模型 API，不仅成本高且隐私边界脆弱；若直接压缩小模型而缺乏针对性微调，又容易出现“答非所问、无依据乱答、partial 题错误否定/错误肯定”等高风险问题。

**工程对策：**项目专门建设了 `ai_engine/finetune_qwen3/` 工程目录，围绕 `Qwen3-1.7B / 0.6B` 开展 Teacher-Student 数据合成、LoRA / Full SFT 对照实验、`Q5_K_M + imatrix` 量化压缩及部署小样本验证。当前统一结论为：`1.7B Q5_K_M + imatrix GGUF` 作为部署主线，`0.6B LoRA` 作为资源受限备选，`1.7B merged` 作为质量基线。

**7. Benchmark 漂移与链路问题定位困难**

**问题描述：**问答能力评测依赖真实 Supabase 数据时，`recent_*` 类问题会随着远端 `model_assets` 的持续更新而发生结果漂移，导致同一模型在不同时间重跑结论不一致，难以判断是 retrieval 漂移还是模型退化。

**工程对策：**新增 retrieval snapshot 冻结机制。先对 benchmark 题集逐题固化检索结果，再在 frozen 口径下复跑各候选模型，将“检索问题”与“回答问题”拆开评估，确保评测结果具备复现性与可审计性。

## 技术可行性分析

BrainDance 项目在技术路线上采取了务实且前沿的设计，将重度计算与轻量交互进行了有效解耦。从当前来看，核心技术闭环已经打通，整体方案具备高度的技术可行性：

**前端交互与状态管理可行性：**移动端基于 Flutter 构建的四主导航结构已稳定运行。在资产展示层（如 recall.dart），系统已成功实现与 Supabase 数据库的直连，能够高效查询 model\_assets 表并渲染瀑布流资产库；在检索层，已从单纯调用 `search-models` 升级为正式接入 `agent-recall`，能够展示 `status / tool_call / tool_result / done` 的流式过程步骤，并自动回传 `session_state / conversation_summary` 支持多轮续聊、预览确认和候选选择；同时仍保留端侧本地问答模型作为弱网或隐私场景兜底。

**移动端 3D 渲染可行性：**当前 3D 查看器并非简单“把网页塞进 WebView”，而是形成了“WebView + 本地 HTTP 代理 + JSBridge + WebGL 渲染器”的完整链路。现阶段仓库中已同时落地两套查看器实现：

1\.**原版查看器（生产主线）：**位于 `3dgs_viewer/my-3dgs-viewer/`，基于 `@mkkellogg/gaussian-splats-3d + Three.js + GSAP`，已实现远程模型代理转发、断点续传与本地缓存、位姿矩阵归一化匹配、初始 `imageId` / `matrix` 目标定位、由相机位姿反推高亮点与镜头飞行、焦距/FOV 换算，以及基于 GSAP 与三次贝塞尔曲线的运镜过渡，可稳定支持 3DGS/Mesh 模型的平滑漫游与参考视角跳转。

2\.**Spark 查看器（实验增强线）：**位于 `3dgs_viewer/spark-3dgs-viewer/`，并已同步打包至移动端 `app/assets/webgl_spark/`。该查看器基于 `@sparkjsdev/spark` 独立搭建 `SparkRenderer + SparkControls + SplatMesh` 渲染链，已实现与 Flutter 现有 `payload` 协议兼容、URL `payload/ply/poses/matrix/imageId` 启动兼容、位姿列表与标签检索、镜头跳转、焦距控制，以及基于 `SplatEdit + SplatEditSdf` 的球形局部高亮特效和基于 `PLANE` 的剖切裁剪特效。它证明项目不仅能“查看高斯场景”，还具备运行时编辑 splat、做空间高亮、语义强调和剖切展示的工程能力。

这说明项目已经具备在主流移动端设备上承载复杂空间模型交互的工程可行性，且预留了从“基础查看”向“可编辑、可特效、可叙事”的空间浏览体验升级路径。

**3DGS 与多 Pipeline 技术路线可行性：**后端 Python Worker 已经从单一路径视频建模，演进为基于 `task_type` 的多流水线分发体系。当前真实接入的类型包括 `video_dual_chain`、`video_3dgs`、`multi_image`、`single_image_sam3d`、`single_image_sharp`、`da3_feed_forward_3dgs`、`da3_sugar`/`da3+sugar`、`da3_2dgs`/`da3+2dgs`、`sparse2dgs`。其中：

1\.**主视频链：**`video_3dgs` 以 Nerfstudio `splatfacto` 为底座，适合高质量真实场景重建；

2\.**快慢双链：**`video_dual_chain` 已落地“先快后慢”的默认策略，快链根据最佳帧选择和场景/单物体判定，在 `single_image_sharp` 与 `single_image_sam3d` 之间自动路由，慢链则继续执行 `video_3dgs` 或 `da3_feed_forward_3dgs`；

3\.**前沿论文组合链路：**`da3_sugar`、`da3_2dgs`、`sparse2dgs` 等链路已在仓库中形成独立 Pipeline，实现“位姿恢复、几何质量、稀疏视角、网格导出”的差异化能力覆盖。

项目并非使用单一算法，而是把真实场景视频、少图输入、单图生成、稀疏视角、快慢链时效和网格提取分配给最合适的算法模块，具备较强的工程鲁棒性和技术演进空间。

**科研前沿性与论文支撑：**BrainDance 当前 3DGS 路线并非停留在 2023 年单篇 3DGS 论文，而是明确吸收了近三年的前沿成果：

1\.**3D Gaussian Splatting for Real-Time Radiance Field Rendering（2023）**：提供实时高质量高斯渲染范式，是项目总体技术基座。

2\.**Nerfstudio: A Modular Framework for Neural Radiance Field Development（2023）**：作为 `video_3dgs` 主链路的工程底座，提供模块化训练、数据管理和 `splatfacto` 实现。

3\.**2D Gaussian Splatting for Geometrically Accurate Radiance Fields（2024）**：支撑 `da3_2dgs` 路线，强调更优几何精度与分钟级训练。

4\.**Sparse2DGS: Geometry-Prioritized Gaussian Splatting for Surface Reconstruction from Sparse Views（2025）**：支撑少图/稀疏视角重建路线。

5\.**SuGaR: Surface-Aligned Gaussian Splatting for Efficient 3D Mesh Reconstruction and High-Quality Mesh Rendering（2023）**：支撑 `da3_sugar` 网格提取与精修路线。

6\.**Depth Anything 3: Recovering the Visual Space from Any Views（2025）**：作为 DA3 路线核心空间恢复模块，增强位姿、深度和统一视觉空间恢复能力。

7\.**Sharp Monocular View Synthesis in Less Than a Second（2025）**：支撑 `single_image_sharp` 快链极速预览能力，直接契合比赛对即时反馈的要求。

8\.**SAM 3D: 3Dfy Anything in Images（2025）**：支撑 `single_image_sam3d` 单图物体生成路线，使单物体链路具备更强的结构化生成潜力。

项目已对这些论文做过定量证据整理。例如：2DGS 在 DTU 上将几何误差从 3DGS 的 `1.96` 降到 `0.80`；Sparse2DGS 在 3-view 设定下将平均 Chamfer Distance 降到 `1.13`；DA3 在多数据集位姿与几何恢复上优于 VGGT、Pi3 等对比方案；SHARP 则直接服务于“单图小于 1 秒级”预览定位。BrainDance 所采用的不是过时方案，而是一条由 2023-2025 年最新科研成果支撑、并已经过工程落地验证的可行技术路线。

**端云异步计算与环境优化可行性：**后端的 Python Worker 节点已具备完整的任务生命周期管理能力。Worker 能稳定轮询（Polling）任务队列，执行视频抽帧、GLOMAP/COLMAP 或 DA3 位姿恢复、3DGS 训练、模型压缩与资产回写。与此同时，项目并未回避新硬件和小显存环境的现实问题，而是在仓库内沉淀了可复现的工程优化方案：

1\.**12GB 家用显卡可跑通：**针对 RTX 5070 12GB，项目通过快慢双链分流、显存门槛检测、手动分阶段加载、模型裁剪与显存流水线控制，使 SAM3D、Nerfstudio 等原本更偏高配环境的链路可以在家用级 Blackwell 显卡上跑通；

2\.**Blackwell 新架构兼容：**针对 RTX 50 系列 `sm_120` 架构，项目在 WSL2 + PyTorch 新版本 + 源码编译 gsplat 的基础上，配套实现了 `ai_engine/3dgs/src/modules/sam3d_engine/mocks.py` 中的 Kaolin/PyTorch3D 兼容 Mock 层，绕开旧三维依赖在 Blackwell 上的编译阻塞；

3\.**失败不降级为伪可用：**当 SAM3D 对显存或依赖不满足时，系统不是简单切回 CPU，而是优先通过路由策略切换到 SHARP 快链或慢链视频重建，既保证 GPU 主路径，又保证任务交付成功率。

**端侧模型可行性：**`ai_engine/finetune_qwen3` 已沉淀完整的训练、评测、量化与部署验证脚本。基于 `Qwen3-1.7B` 的 LoRA/merged/GGUF 以及 `Qwen3-0.6B` 的轻量备选方案，项目已验证“本地小模型 + 检索证据 + formatter 兜底”在真实数据场景下具备可运行性，且 `1.7B Q5_K_M + imatrix` 已成为当前推荐部署主线。

综上所述，“**移动端低门槛采集** + **双查看器空间浏览** + **多论文驱动的 3DGS 多 Pipeline 重建** + **Blackwell/12GB 环境优化** + **端侧轻量问答智能**” 的系统架构并非理论设想，而是已经落地并持续迭代的可行技术方案。

## 市场可行性分析

在空间计算（Spatial Computing）时代爆发的前夕，BrainDance 的产品立意具有极强的前瞻性与现实意义。

**1.空间计算处于蓝海起步期：**Apple Vision Pro 的发布，标志着空间计算从概念验证进入主流消费电子议程。项目组调研显示，IDC 与 Counterpoint 对 2025 年全球 XR 设备出货量的预测已达到约 1400 万至 1500 万台。硬件端正在快速起量，但原生 3D 内容供给依然严重不足，这意味着“低成本空间内容生成”本身就是产业链中的关键缺口。BrainDance 并不和头显硬件正面竞争，而是切入更现实、更稀缺的内容供给环节，定位清晰。

**2.市场痛点非常明确：**当前普通用户记录空间仍主要依赖照片、视频和少量全景图，这些媒介几乎都不具备真正的 6DoF 交互能力。专业三维建模、激光扫描和数字孪生成本高、周期长、需专业团队，难以进入大众日常生活。BrainDance 通过“普通手机采集 + 云端高斯重建 + 空间检索 + 双查看器沉浸浏览”的组合，把原本需要专业设备和专业人员完成的工作，压缩为普通用户可理解、可上手、可消费的服务。

**3.情感消费需求具备刚性：**快速城市化使大量老街、胡同、社区和生活空间不断消失；与此同时，毕业、搬家、亲人老去、旧居迁移等个人经历又不断制造“想留住空间”的真实需求。用户真正怀念的往往不是一张照片，而是“我还能不能再走进去看一眼”。BrainDance 的价值不止于生成一个 3D 模型，而是提供一种可以被重新进入、重新检索和重新叙事的数字记忆形式，这类情感消费具有明确的长期需求基础。

**4.银发经济与数字疗法方向存在高潜力场景：**根据 Rubin 等人（1986）提出的“怀旧隆起（Reminiscence Bump）”理论，老年人对 10-30 岁期间的自传体记忆最为深刻。护理学研究指出，老年人在更换居住环境时容易出现迁移压力综合征（Transfer Trauma）。BrainDance 利用 3DGS 的高保真空间复现能力，可尝试为失智照护、迁居安抚、熟悉环境回访等场景提供非药物干预（NPIs）式的数字疗法工具。这使项目不仅是“酷炫的 3D 展示”，还具备明确的社会价值与银发经济切入点。

**5.差异化竞争优势明显：**相比传统 3D 建模，BrainDance 在成本、时间和门槛上均形成降维优势。传统方案常需要专业扫描设备、专业团队和数天周期，而 BrainDance 以手机为入口、以小时级或分阶段交付为目标，明显更适合 C 端与中小 B 端场景。相比现有竞品，项目也有清晰区隔：

1\.相较于偏“播放器”属性的方案，BrainDance 不只提供模型播放，还加入自然语言搜索、语义高亮、位姿跳转和 Spark 特效浏览；

2\.相较于立体视频类方案，BrainDance 提供的是可漫游的体积式 6DoF 场景，而不是只能站在原位观看的双目视频；

3\.相较于高质量 Web 3D 场景平台，BrainDance 更强调移动端真实采集闭环、时效性双链交付和面向记忆/空间档案的语义检索能力。

**6.商业模式具备延展空间：**项目可同时覆盖 C 端与 B 端。C 端可发展为订阅制的“空间记忆留存与管理服务”；B 端可服务于房地产样板间复看、文旅空间数字留档、社区改造档案、医疗与养老机构环境复原等场景；进一步沉淀后，还具备形成城市空间数字档案和 UGC 3D 场景库的数据价值。

**7.稳健的市场推进策略：**尽管潜在市场空间广阔，但本项目的市场策略保持克制与务实。当前阶段不作过重的商业变现承诺，而是将核心精力聚焦于“最小可行性产品（MVP）”的打磨：先跑通核心采集闭环、验证双查看器浏览体验、验证快慢双链带来的即时性收益、提升极端画质和普通显卡环境下的生成鲁棒性。通过先把“内容生成和空间检索”这两个最关键的价值点做深，再向商业服务和平台化生态扩展，市场路径更稳健，也更符合学生项目向真实产品演进的节奏。

## 性能需求

### 时间特性

在 3D 空间计算的端云架构中，“计算耗时”与“交互响应”是不可避免的核心矛盾。系统在工程上采取了严格的异步解耦与分层时效性设计，以确保绝大部分前端交互操作不被长耗时的重建（如 3DGS 训练）过程所阻塞：

**前端非阻塞异步化：**任务一旦创建即刻转入 pending 状态的后台队列，用户可无缝切换至其他应用功能。

**搜索链路的极速响应（语义解析与向量化）：**

**自然语言意图解析：**系统对接了专门优化的 qwen-turbo 大语言模型，极大提升了对用户非结构化空间描述（如“上周桌子旁边的杯子”）的解析速度。

**语义特征对齐：**采用高性能的 text-embedding-v2 模型进行文本向量化。

**时间维度约束：**内置了时间词解析与日期规范化逻辑，将时间范围约束直接转化为数据库前置过滤条件，大幅缩小向量检索池，保障秒级返回。

**快慢双链的分层时效保障：**系统在三维生成链路中引入了“单任务入口、双阶段交付”的快慢双链机制。用户提交一次视频任务后，Worker 会先抽样候选帧，完成最佳帧选择与场景/单物体判定；若判定为场景，则快链优先进入 `single_image_sharp` 生成极速预览，若判定为单物体且显存满足门槛，则快链切换到 `single_image_sam3d`，否则自动降级到 SHARP，以保证第一阶段结果尽快可见。快链完成后，系统立即对同一 `scene_id` 执行一次资产 Upsert，使 Recall 页面先出现可浏览的预览卡片；随后再自动接续 `video_3dgs` 或 `da3_feed_forward_3dgs` 等慢链，完成更高质量的位姿估计、训练与细节恢复，并以同一 `scene_id` 覆盖式回写最终结果。这样既满足“先反馈、后收敛”的时效目标，也避免同一场景出现两张重复卡片破坏用户体验。

**快慢链容错策略：**若快链失败，系统记录日志后继续尝试慢链；若慢链失败但快链成功，任务仍可作为可交付结果保留为 `completed`；仅当快链与慢链同时失败时才会标记为 `failed`。这种状态机策略保证了“时效性”不是口号，而是落实为明确的工程决策。

**端侧本地问答的轻量部署：**

**量化部署主线：**当前推荐候选为 `1.7B Q5_K_M + imatrix GGUF`，在保持知识不明显磨损的前提下显著降低内存占用，满足 Android 端侧部署条件。

**候选版本策略：**`1.7B merged` 作为质量基线，`0.6B LoRA` 作为资源受限机型的备选方案，便于按设备能力做差异化下发。

**交付链路的格式压缩与容错机制：**

**动态交付格式：**模型交付严格支持通过任务参数 (task\_params) 选择 .splat、.ksplat 或原始 .ply 等多模态 delivery\_format，以在不同阶段兼顾下发速度与精度。

**极致的压缩率优化：**项目组内部实测表明，采用特定的高斯球压缩算法（如转为 .splat 格式），在牺牲极小视觉保真度的前提下，可将 3D 模型文件体积缩减约 90%，使得移动端弱网环境下的模型首次加载时间从通常的 20s 级断崖式下降至约 2s 级（具体耗时受机型与网络带宽波动影响）。

**状态机流转容错：**为防止极端场景下的压缩超时导致任务卡死，Worker 内置了失败回退机制——若压缩失败，自动回退上传未压缩的 .ply，确保任务生命周期始终能稳健推进至 completed 或 failed 的明确终态。

**时效性双链架构（快慢链调度）：**


**1. 单任务入口，降低操作复杂度：**前端只提交一次 `video_dual_chain` 任务，用户不需要手动在“快速预览”和“高质量生成”之间做技术性选择。

**2. 快链以时效优先：**快链负责在较短时间内形成可浏览的预览结果，让用户立即知道系统已经理解并开始处理其拍摄内容，适用于现场展示与真实使用中的即时反馈诉求。

**3. 慢链以质量优先：**慢链默认使用 `video_3dgs`，也可配置切换至 `da3_feed_forward_3dgs`，重点保障几何完整性、视角稳定性与细节保真度，用于最终资产沉淀。

**4. 单场景渐进更新：**快链先写入一次 `model_assets`，慢链完成后再对同一 `scene_id` 覆盖式 Upsert，前端只保留一张场景卡片，体现“同一记忆逐步变清晰”的产品逻辑。

**5. 任务路由有明确工程规则：**Worker 会先抽样候选帧并执行最佳帧选择，再通过 VL 判定 `scene/object`。若为场景，快链直接走 `single_image_sharp`；若为单物体，则先检查显存，显存大于等于阈值时走 `single_image_sam3d`，否则自动降级回 `single_image_sharp`。这保证“快”不是简单粗糙，而是有清晰技术判断和资源感知的智能快链。

**6. 失败策略契合赛题中的服务连续性：**若快链失败，系统仍继续执行慢链；若慢链失败但快链成功，任务仍可作为 `completed` 交付；只有快慢链同时失败时才记为 `failed`。也就是说，项目将“即时性服务”落到了真正的状态机和交付策略上，而非仅停留在宣传口径。

**7. 展示价值明确：**相较于传统“提交后长时间等待”的单链方案，快慢双链把“场景化响应”和“即时性服务”具体落实到任务编排、算法路由、状态回写与前端呈现上，更能体现项目对移动端真实用户体验的理解。

# 概要设计

## 处理流程

BrainDance 系统的核心主业务流程围绕“端到端的异步三维资产生成”与“空间检索/问答”展开，链路如下：

1\. 用户在移动端录制视频或选择图片素材。

2\. 文件通过授权直传到 Supabase Storage 的 {user\_id}/{scene\_id}/raw/ 目录。

3\. 前端将任务元数据写入 processing\_tasks 表，状态标记为 pending。

4\. 后端 Python Worker 轮询并锁定任务（转为 processing），下载素材并调用对应的 AI 流水线生成模型。

5\. Worker 将结果（point\_cloud.\*、transforms.json、preview.jpg）上传至 output/ 目录。

6\. Worker 提取语义特征，在 model\_assets 表执行 Upsert（入库）操作，任务完成。

7\. 用户在 Recall 页浏览新资产，通过搜索并进入 WebGL 查看器体验沉浸式漫游。

8\. 当用户发起空间问答时，系统优先组织 retrieval 证据；在端侧能力可用时，本地 `Qwen3` 模型依据证据生成短答或执行安全拒答。

## 总体结构设计

系统采用“**移动交互层 + BaaS 中枢层 + AI Worker 层 + 端侧模型层**”的混合分层架构，实现交互、调度、重计算与轻量本地智能的解耦：

**表示层（移动端交互层）：**由基于 Flutter 的跨平台移动端 App 构成。包含 Login、四大主导航（Recall、Record、Generate、Settings）与 Viewer。专注用户体验、传感器调用与轻量数据组织。

**服务与数据层（BaaS 中枢层）：**由 Supabase 平台构成。整合了 Auth、DB（关系表、向量检索与记忆专题数据）、Storage（对象存储）、Realtime 和 Edge Function，负责全局状态流转与数据一致性。

**智能计算层（AI Worker 层）：**由部署在 GPU 节点上的 Python Worker 集群构成。负责重计算与复杂 3DGS/语义分析流水线的异步执行。

**端侧智能层（Local QA 层）：**由已量化的 `Qwen3` 模型、本地 RAG、formatter 与路由策略组成。负责移动端低延迟问答、证据约束输出与弱网场景兜底。

## 功能设计

**移动端（Thin Client）：**专注“交互与轻量组织”，卸载繁重计算。

**BaaS 中枢：**专注“数据与中间调度”，作为系统唯一的数据真相源。

**AI Worker：**专注“重计算与资产入库”，作为无状态的消费机器，可随时重启与横向扩容。

**端侧模型层：**专注“轻推理与回答约束”，把复杂大模型能力压缩进适合移动端运行的部署形态。

## 数据流转设计

为了满足复杂的业务场景，系统数据流转采用严格的路径规划：

**输入阶段：**原始素材严格进入隔离的 raw/ 目录；任务配置记录进入 processing\_tasks。

**加工阶段：**Worker 根据 task\_type（如视频或图片流水线）下载对于路径的素材。

**输出阶段：**生成结果进入 output/ 目录；元数据及空间语义标签进入 model\_assets 并建立 pgvector 索引。

**检索阶段：**基础语义搜索由 `search-models` 提供向量检索能力；正式 Recall 交互由 `agent-recall` 统一编排，根据查询在空间检索、资产整理、时间对比和记忆摘要等模式之间路由，再返回 `answer / evidence / actions / follow_up / session_state` 等结构化结果。

**问答阶段：**若启用本地问答，系统将 retrieval 命中结果、证据摘要与 query_class 路由结果传入端侧模型；必要时通过 formatter 兜底，输出受约束的最终答案。

## 错误/异常处理设计

### 错误/异常输出信息

系统能够截获并输出包括：上传失败/断网、搜索参数非法、AI 评分不通过（如图像模糊）、模型特定格式压缩超时、查看器运行平台不支持等维度的异常信息。

### 错误/异常处理对策

1.采集上传失败时，保留本地素材缓存并提示用户重试。

2.AI 位姿解算评分不通过时，Worker 将详细报错原因写入 quality\_score 与 quality\_reason，前端给与重拍提示。

3.任务执行异常崩溃时，系统正确捕获堆栈日志并将数据库任务标记为 failed。

4.当特定优化格式（如 .ksplat）转换引发 OOM 失败时，Worker 自动回退机制将上传未压缩的原始 .ply 文件，保证模型可用。

5.检测到在非移动端（纯 Web/桌面端）运行应用时，在初始化阶段拦截提示，引导切换至 Android 真机。

6.日志同步采用“内存缓冲 + 全量覆盖上传”策略，减少并发覆盖导致的日志丢失。

7.下载远程模型时若 HTTP 非 200，解析错误体并抛出，前端直接 toast 具体错误，方便现场排障。

8.搜索接口异常时优先使用 Edge Function 回传的 details.error，避免只显示笼统“请求失败”。

## 系统配置策略

系统配置坚决摒弃硬编码：移动前端通过 .env 环境注入基础网关与匿名公钥；Python Worker 根据系统环境变量动态读取 Supabase 凭证、指定自身的工作目录（存储桶/表名）及模型默认交付格式组合。这种解耦便于在不同环境下快速切换上下文。

## 系统部署方案

**本地联调环境：**运行 supabase start 一键启动本地容器化 BaaS 基础设施 → 在带 GPU 的开发机执行 python src/worker.py 拉起消费节点 → 手机端或模拟器执行 flutter run 接入局域网测试。

**本地问答实验环境：**使用 `conda run -n qwen3_ft` 执行 `ai_engine/finetune_qwen3/` 下的训练、评测、merge、量化与部署验证脚本；端侧通过 `GGUF + llamadart` 路线进行集成验证。

**云端生产环境：**Supabase 服务由云服务器承接鉴权与数据吞吐；Python Worker 镜像部署至拥有 L20 等显卡的云 GPU 节点阵列。

## 跨端应用架构设计

BrainDance 现阶段明确以智能手机为核心硬件入口。架构上采用了 “**原生 Flutter** + **内嵌 Web 3D 引擎**”的混合跨端模式。Flutter 负责高可用地抹平设备差异，而内嵌 WebView 负责统一模型渲染表现。此架构在保证当前可用的同时，为未来向 Apple Vision Pro 或 Android XR 终端的原生适配预留了标准的剥离接口。

## 其他相关技术与方案

在架构细节上，项目沉淀了诸多工程实践：

**无中间件直传（Direct-to-Storage）：**放弃传统的业务服务器代理中转，前端凭票据直接上传大文件，大幅减轻服务器 OOM 风险。

**基于 Realtime 的事件驱动推送：**移动端放弃高频轮询，改用 WebSocket 订阅数据库变更通道，任务状态变动实时推送到端侧，降低功耗与请求开销。

**多模型交付格式动态支持：**后端通过 delivery\_format 参数，同时支持大体量原模和专为 Web 端剪枝压缩的轻量格式。

**统一任务底座：**不同模态（单图、多图、视频）的三维生成任务均抽象复用同一套任务表与资产表结构，极大地增强了系统的可扩展性。

# 数据库设计

BrainDance 系统的底层存储架构摒弃了传统单一关系型数据库的局限，创新性地采用 “**关系型元数据管理** + **对象存储大文件托管** + **向量检索空间查询**” 的混合多模态数据库设计。依托 Supabase（基于 PostgreSQL）的强大生态，系统核心存储结构被极简而高效地抽象为“两张核心表 + 一个核心存储桶”。

# 手机端侧部署设计

考虑到三维内容采集与渲染对硬件资源的极高要求，本系统采取了“重端侧能力调用，轻端侧业务计算”的部署策略。

## 手机环境需求

为保证系统的可用性与渲染帧率，移动端部署需满足以下基础环境约束：

**操作系统：**支持主流的 Android 运行环境。当前代码中已明确，桌面端（Windows/macOS）与纯 Web 端暂时不作为主要部署与适配目标，以聚焦移动体验。

**硬件权限与传感器：**App 必须成功获取设备的加速度传感器和高清摄像头调用权限（用于视频/单图取景录制）与本地文件读写权限（用于素材暂存）；

**网络与渲染通信：**设备必须具备稳定的网络以访问 Supabase 的鉴权与数据网关；操作系统必须提供支持 WebGL 2.0 的现代 WebView 内核，以满足 Flutter 的 webview\_flutter 插件对 3DGS 渲染引擎的承载要求。

**端侧模型部署条件：**若启用本地问答能力，设备需具备满足 GGUF 模型运行的可用内存空间与稳定的本地推理运行时；不同机型可按 `1.7B Q5_K_M + imatrix` 或 `0.6B LoRA` 候选做差异化配置。

**标定测试设备：**根据项目基准测试，当前的移动端部署与真机联调工作主要在 OPPO Find X8 与 OPPO Reno 14 两款安卓旗舰/次旗舰设备上进行，运行表现稳定。

# 详细设计

本节将对系统中最具代表性的三个核心模块进行描述，涵盖数据输入、输出流转及当前工程的限制条件。

## 回忆检索与查看模块

### 功能描述

该模块是用户进入应用后的第一触点。它负责直连数据库拉取 `model_assets` 中的历史资产并渲染为视觉卡片。当用户在顶部输入自然语言（如“寻找桌上的红杯子”）时，模块会优先通过 `agent-recall` 发起统一 Agent 查询，由后端根据问题在空间检索、资产整理、时间对比或记忆摘要等模式之间路由；若只是基础检索，则底层仍复用 `search-models` 的向量能力。命中后，模块将结构化动作中的模型路径、场景 ID 与位姿参数传递给 3D 查看器，实现精准的“定位跳转”。

### 性能描述

作为超高频交互模块，其核心性能要求是“非阻塞与极速响应”。模块采用了“轻前端 + 远程数据 + 本地渲染桥接”的架构：列表刷新与向量匹配均由后端的 PostgreSQL 承担，移动端不执行任何重计算；模型查看则通过在本地拉起一个微型 HTTP 代理服务来绕过 WebView 的跨域限制，确保 3D 资产的平滑加载。

### 输入

1.用户触发下拉刷新的动作指令。

2.用户在搜索框键入的自然语言文本（String）。

3.数据库 model\_assets 返回的 JSON 格式资产记录。

4.`agent-recall` 或 `search-models` 返回的结构化结果对象，包括相似度评分、模型 URL、目标坐标（Pose）、动作协议与续聊上下文。

### 输出

1.Recall 页面渲染的瀑布流模型预览卡片。

2.过滤后的搜索结果列表视图。

3.唤起沉浸式的 3D WebGL Viewer 页面，并触发相机的平滑推拉动画。

### 程序逻辑

1\. 页面初始化，发起 Supabase DB 查询，按时间戳降序挂载数据。

2\. 监听搜索框 onSubmit 事件，优先向 `agent-recall` 云函数发送携带鉴权 Token 的请求；需要基础检索时再调用 `search-models`。

3\. 解析返回结果中的 `actions[].payload`、候选项与 `follow_up`，提取目标模型的 `ply_path`、位姿矩阵或下一轮建议输入。

4\. 用户点击结果卡片，路由跳转至 WebGLViewer 页面。

5\. Flutter 宿主通过 JSBridge 向内嵌的 WebView 注入模型 URL 与特定的 Camera Target 坐标，驱动 WebGL 内核加载并完成漫游动画。

### 限制条件

1.强依赖移动端 WebView 内核对 WebGL 的显存分配限制，若单一模型过大（如未经压缩的 500MB+ .ply），极易导致 iOS Safari 或 Android WebView 发生 OOM 崩溃。

2.定位跳转的精准度高度依赖后端 AI 导出的位姿文件完整性。
3.Agent 的创作模式和弱图谱模式当前仍属于增强能力，正式前端已能消费结果，但对应的完整专用卡片与创作产出流水线尚未全部闭环。

## 视频采集与任务创建模块

### 功能描述

该模块是“空间数字化”流程的绝对起点。它通过封装底层相机硬件，提供全屏沉浸式的录制界面，并结合设备传感器指导用户围绕目标物体或场景进行环绕扫描。当前实现中，Record 页接入了加速度计、用户加速度流与磁力计，对手机运动强度、瞬时抖动与朝向进行实时估计，再通过 HUD、状态提示与触觉反馈引导用户保持稳定运镜。录制结束后，模块自动抽帧生成缩略图，并跳转至 VideoSubmitPage 引导用户填写资产名称，为后续的 3DGS 训练准备数据源。

### 性能描述

相机的启动延迟必须控制在 500ms 内，取景器要求维持在 60fps 以防用户产生眩晕感。为了防止产生不可控的超大视频文件导致后续上传瘫痪和服务器显存溢出，模块在代码层面硬性植入了 180 秒的强制录制时长上限。

### 输入

1.物理摄像头的实时高帧率视频流。

2.用户的录制启停手势。

3.用户在提交页面填写的场景名称 (display\_name)。

### 输出

1.暂存在设备沙盒缓存目录下的原始 .mp4 视频文件。

2.多模态 LLM 选择的视频代表性帧 (.jpg)。

3.封装好的待提交任务元数据对象。

### 程序逻辑

1.初始化 camera 控制器，绑定设备后置主摄并配置分辨率。

2.用户点击录制按钮，启动文件写入流；达到 180 秒上限时自动终止。

3.调用插件提取首帧作为缩略图，路由压栈跳转至信息补全页 (VideoSubmitPage)。

4.用户完善名称并点击提交。

### 限制条件

当前的主要瓶颈在于端到端闭环逻辑的彻底联通，尚未到达大规模公测阶段。环境光线过暗或用户剧烈抖动将直接导致产出素材不符合 3D 重建要求。

## 云端重建与资产入库模块 (Python AI Worker)

### 功能描述

作为隐藏在幕后的“算力巨兽”，部署在带 GPU 服务器上的 Python Worker 是整个大脑。它持续且静默地轮询任务表，利用工厂模式 (PipelineFactory) 动态实例化不同的 AI 算法管线（如基于视频的高质量 3DGS、基于单图的 SAM3D 语义分割等）。它不仅负责算力炼丹，还包揽了模型压缩、云端上传、失败重试及数据库最终回写的全部脏活累活。

### 性能描述

该模块属于典型的**异步长耗时后台任务**（单任务耗时从几秒到数十分钟不等）。其设计核心不在于“快”，而在于**“高鲁棒性与可恢复性”**。无论发生显存溢出、网段还是算法崩溃，Worker 都必须能捕获异常，将日志写入表内，保障进程不致于整体宕机。

### 输入

1.数据库 processing\_tasks 表中状态为 pending 的记录。

2.从 braindance-assets/raw/ 路径下流式下载的原始 video.mp4 或 image.png。

3.环境变量中下发的默认模型交付格式配置（如优先输出 .splat）。

### 输出

1.算法产出的三维格式文件（point\_cloud.ply, point\_cloud.splat 等）。

2.用于前端快速展示的降采样预览图 (preview.jpg)。

3.包含空间坐标映射系的 transforms.json。

4.向 model\_assets 表执行 Upsert 插入的新资产记录，以及更新至 completed/failed 的最终任务状态。

### 程序逻辑

**1.轮询锁定：**Worker 守护进程定期轮询 pending 任务，利用数据库行锁或原子更新将其状态变更为 processing 以防重复消费。

**2.素材就绪：**基于记录的 Storage 路径，将素材下载至 Worker 节点的本地临时工作区。

**3.管线分发：**根据 task\_type 创建对应的 Pipeline 实例：

video\_dual\_chain（默认视频双阶段任务入口，由 Worker 内部编排快链与慢链）

video\_3dgs（传统高精度视频 3DGS 重建主链）

multi\_image（多图输入重建链路）

single\_image\_sam3d（结合 SAM 3D Objects 的单图 3D 物体生成）

single\_image\_sharp（基于 SHARP 的单图极速预览生成）

da3\_feed\_forward\_3dgs（Depth Anything 3 驱动的前馈式 3DGS 生成）

da3\_sugar / da3+sugar（DA3 + SuGaR 组合链路，偏向网格提取与高质量精修）

da3\_2dgs / da3+2dgs（DA3 + 2DGS 组合链路，偏向更优几何精度）

sparse2dgs（少图/稀疏视角 2DGS 重建链路）

**4.模型压缩与上传：**算法执行完毕后，调用压缩脚本生成利于 Web 传输的格式，并通过 Supabase SDK 批量推送至 output/ 路径。

**5.元数据入库：**整合生成的模型路径、特征向量、物品列表，向 model\_assets 发起插入请求。

**6.状态流转：**标记任务完成，并清理本地临时文件。

### 关键工程优化点

1.任务类型分发由工厂统一管理，新增 pipeline 时不需要改 Worker 主流程。

2.AI 分析元数据（评分/标签/描述）在模型生成后立即同步回任务与资产表。

3.webgl\_poses.json 上传时同步 image\_url，支持 Recall 搜索结果中的关键帧可视化。

F4.inally 阶段强制清理源文件和工作区，降低长期运行时磁盘占用。

### 限制条件

1.强依赖 NVIDIA GPU 环境（需支持 CUDA 12.8+）及充足的 VRAM。

2.对于引入的前沿实验性链路（特别是 DA3 、 SAM 3D Objects 与 SHARP 单图生成算法），当前架构虽已跑通接口接入能力，但其泛化性与生成质量仍在持续标定与验证中。

3.模型压缩阶段存在容错风险：若特定的轻量化格式（如 .ksplat）转换失败，系统需触发回退机制，强制上传原始的 .ply 文件兜底。

## 本地问答与端侧模型模块

### 功能描述

该模块承载 BrainDance 在移动端“可离线、低延迟、隐私友好”的空间问答能力。它并不直接记忆用户事实，而是围绕检索证据进行回答约束：当 retrieval 命中时，模型依据证据生成短答；当证据不足或无命中时，模型执行明确拒答，避免生成无依据内容。

### 性能描述

该模块属于“中等耗时但强交互感知”的轻推理链路。与云端大模型 API 相比，其核心目标不是绝对最强推理能力，而是**在移动端有限内存与较弱网络条件下保持稳定、可信、低幻觉**。当前部署主线候选为 `1.7B Q5_K_M + imatrix GGUF`。

### 输入

1.用户输入的自然语言问题。

2.本地或云端 retrieval 返回的命中证据、物体列表与场景摘要。

3.query\_class、formatter route、answer route 等链路中间结果。

4.候选模型配置（如 `1.7B Q5_K_M + imatrix`、`0.6B LoRA`）。

### 输出

1.面向用户的简洁问答结果。

2.在 `--show_trace` 或调试模式下可观测的 route、evidence 与 answer 轨迹。

3.strict / OOD / frozen benchmark 的评测日志与候选对比摘要。

### 程序逻辑

1\. 系统先执行 retrieval，尽量命中正确证据。

2\. 根据 query 类型将问题路由到 object lookup、recent list、partial coverage 等不同处理分支。

3\. 若命中证据充分，则把证据摘要与回答约束词一并送入本地模型。

4\. 若命中证据不足，则由 formatter 或拒答模板优先兜底，防止模型幻觉扩散。

5\. 输出最终答案，并在调试模式下记录 route、evidence、latency 与结果标签。

6\. 新模型上线前必须经过 strict、未见数据 OOD、空间 hardcases 与 deployment eval 的组合验证。

### 关键工程优化点

1.通过 Teacher-Student 合成数据与 LoRA SFT，训练模型学会“基于证据回答”而非自由发挥。

2.通过 `Q5_K_M + imatrix` 量化，在显著压缩体积的同时尽量保留微调后的任务纪律性。

3.通过 retrieval snapshot 冻结复现机制，拆分检索漂移与回答退化，提升 benchmark 的解释力。

4.通过统一版本矩阵与横评总览，避免候选模型状态分散在零碎日志中难以对比。

### 限制条件

1.当前空间关系高难题更多暴露为 retrieval / formatter 问题，尚未完全进入纯模型能力竞争阶段。

2.本地问答链路当前仍以实验/候选部署形态存在，尚未完全并入正式产品主流程。

3.`recent_*` 类问题对远端数据库增量极其敏感，若不冻结 snapshot，评测结果会发生漂移。
