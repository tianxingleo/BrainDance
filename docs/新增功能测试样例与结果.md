### 测试结果综合分析及建议

从 UT-27 至 UT-32 的执行结果看，社区功能的单元测试重点覆盖了"地图区域筛选、标签附近筛选、地图标记选择、标记上限偏好、帖子模型拷贝、投稿草稿序列化"六类核心纯逻辑。测试结果均通过，说明新增社区功能中最容易被 UI 操作频繁触发的基础函数具备可回归验证能力。

这批用例的一个特点是尽量把社区复杂交互拆回可独立断言的数据逻辑。例如区域筛选不直接依赖 `flutter_map`，地图标记选择不依赖真实地图渲染，草稿测试不依赖文件系统。这样可以在较低成本下覆盖地图、投稿和详情页背后的关键规则。

后续建议继续补充 Repository 层的可测试性改造。当前 `CommunityRepository` 直接读取 `Supabase.instance.client`，对假客户端注入不够友好，导致创建贴文、元数据更新、评论追加等逻辑更适合在功能测试中验证。若后续把 SupabaseClient 改成构造注入，可以进一步把发布、点赞、收藏、评论等写入逻辑下沉为更稳定的单元测试。

### 测试经验总结

社区功能的单元测试不能只围绕 Widget 展示做断言，地图和筛选类能力更适合优先抽成纯函数测试。UT-27 至 UT-29 的结果说明，只要把 bounds、tag、radius、marker quota 这些规则从页面状态中拆出来，就能用少量样例覆盖大量边界条件。

第二个经验是，地图功能必须主动覆盖反子午线、无效坐标、空 bounds 和本地偏好异常值。普通城市范围测试通常很容易通过，但这些边界场景才是上线后产生"地图空白""标记突然消失""列表被误清空"等问题的根源。

第三个经验是，社区互动的乐观更新需要模型层保持严格的不可变拷贝语义。UT-31 明确验证了 `copyWithRealId` 不丢失多模型图片和模型路径，这比单纯看页面数字变化更能防止发布后链路断裂。

### 测试结果综合分析及建议

从 UT-33 至 UT-38 的结果看，Agent Chat 的单元测试覆盖了"流式事件解析、最终响应恢复、会话模型序列化、执行模式判定、done payload 兼容、后端请求 schema"六类关键逻辑。测试重点集中在前后端协议边界和本地状态恢复，这些正是 Agent Chat 区别于普通搜索页的主要风险点。

后续建议把 `_resolveExecutionMode`、`_normalizeAgentDonePayload` 这类页面私有扩展逻辑抽成可导出的纯函数。当前测试设计可通过同库测试实现，但抽离后可以减少 Widget Harness 成本，也能让协议兼容逻辑更容易持续回归。

### 测试经验总结

Agent Chat 的单元测试不能只验证 `AgentRecallResponse.fromJson` 是否能跑通，还必须覆盖流式事件的"半包、重复、不同包装层、不同协议格式"。这些问题通常不会在普通 JSON 接口测试中暴露，但会直接影响聊天页是否能持续显示进度。

第二个经验是，多轮 Agent 的测试需要把本地会话状态当作核心数据，而不是临时 UI 状态。`session_state`、`conversation_summary` 和 `short_term_memory` 如果无法落库恢复，确认执行、候选续聊和个性化上下文都会失效。

### 测试结果综合分析及建议

从 FT-23 至 FT-29 的结果看，新增社区功能已经覆盖"发布、浏览、详情互动、地图探索、区域标签筛选、搜索历史、离线恢复"七条核心用户路径。测试结果均达到预期，说明社区模块已具备从个人模型资产到公共空间记忆浏览的完整闭环。

其中，FT-23 验证了模型资产向社区贴文转换的发布链路，FT-24 和 FT-25 验证了社区流、详情页和互动 metadata 的读写一致性，FT-26 和 FT-27 验证了地图标记与探索页筛选联动，FT-28 覆盖轻量搜索体验，FT-29 则补足了移动端断网与草稿恢复场景。

需要重点关注的剩余风险是权限边界。当前 `community_posts` 迁移仍使用开发态全开放 RLS，本轮测试只能证明客户端侧的可见性过滤有效，不能证明数据库层已经具备生产级隔离能力。后续在收紧 RLS 后，应增加 anon/authenticated/service_role 三类角色的读写权限回归，并验证非所有者不能修改或删除他人贴文。

### 测试经验总结

社区功能测试的核心经验是，"发布成功"不是终点，必须继续验证发布后的浏览、详情、Viewer、互动和个人页统计是否都能消费同一条数据。FT-23 至 FT-25 串联后可以确认一条贴文从写入到后续互动的生命周期没有断点。

第二个经验是，地图功能需要同时测算法稳定性和交互路径。单独看到标记显示并不够，还要验证上限调整、缩放不洗牌、点击详情、长按聚合和 viewport 回传。FT-26 与 FT-27 组合后，才能较完整地覆盖社区地图从空间索引到内容筛选的实际体验。

第三个经验是，移动端社区模块必须把离线和草稿作为主路径的一部分来测。社区发布依赖网络，但用户填写内容的过程很容易被切后台、断网或误退打断；FT-29 证明草稿和重试机制可以降低这类场景下的数据丢失风险。

FT-36 通过说明 Agent Chat 的后端事件链可以通过桌面 CLI 复现。该用例能帮助区分问题发生在后端事件生成、HTTP 流传输，还是 Flutter 事件消费与展示阶段，是 Agent Chat 联调的关键辅助路径。

### 测试结果综合分析及建议

从 FT-30 至 FT-36 的结果看，Agent Chat 功能已经覆盖"首次会话、流式问答、多轮写操作确认、时间对比、异常 fallback、多会话管理、桌面协议复现"七条关键路径。测试样例同时覆盖 Flutter 本地状态、SQLite 会话历史、Supabase Edge Function 流式协议和 LangChain 共享 Core 返回结构。

后续建议把 FT-31 与 FT-36 固化为联调固定组合：先用 CLI 确认后端事件和 `done` payload 正常，再用 Flutter 页面验证事件消费与 UI 恢复。这样可以快速定位问题属于后端生成、网络传输还是前端展示。

### 测试经验总结

Agent Chat 的功能测试必须把"过程"当成可验证结果，而不仅是最终回答。用户看到的连接态、工具调用、候选卡片、跟进提示和耗时，都是 Agent 产品体验的一部分，因此 FT-31 明确把流式事件顺序和持久化一起纳入验收。

第二个经验是，写操作和普通问答必须分开测试。FT-32 的 preview/execute 闭环证明，Agent Chat 不是简单聊天窗口，而是具备实际写库能力的操作入口；因此所有写操作都必须验证预览不写库、确认才写库。

第三个经验是，Agent Chat 的异常测试要覆盖"流失败但 JSON 成功"和"两条链路都失败"两类情况。只测最终失败会遗漏 fallback 重复落库风险，只测 fallback 成功又会遗漏用户看到受控错误的体验。
