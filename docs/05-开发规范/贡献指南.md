## 🔄 开发工作流

### 1. Fork 项目

首先，Fork BrainDance 仓库到您的 GitHub 账户：

1. 访问 [BrainDance GitHub 仓库](https://github.com/tianxingleo/BrainDance)
2. 点击右上角的 **Fork** 按钮
3. 选择您的 GitHub 账户作为 Fork 目标

### 2. 克隆仓库

```bash
# 安装并初始化 Git LFS（仅首次需要）
git lfs install

# 克隆您的 Fork 到本地（必须带全部子模块）
git clone --recurse-submodules https://github.com/YOUR_USERNAME/BrainDance.git

# 进入项目目录
cd BrainDance

# 拉取 LFS 大文件（主仓库 + 所有子模块）
git lfs pull
git submodule foreach --recursive 'git lfs pull || true'

# 添加上游仓库（用于同步最新代码）
git remote add upstream https://github.com/tianxingleo/BrainDance.git
```

### 3. 创建功能分支

```bash
# 确保在主分支最新代码基础上创建分支
git checkout dev
git pull upstream dev

# 创建新分支
# 分支命名规范：<类型>/<描述>/<作者>
# 例如：feat/user-auth/tianxingleo
#      fix/video-upload-bug/tianxingleo
#      docs/improve-readme/tianxingleo

git checkout -b feat/your-feature-name
```

**分支类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat/add-semantic-search` |
| `fix` | Bug 修复 | `fix/video-upload-timeout` |
| `docs` | 文档更新 | `docs/improve-api-doc` |
| `refactor` | 代码重构 | `refactor/optimize-pipeline` |
| `test` | 测试相关 | `test/add-unit-tests` |
| `chore` | 构建/工具 | `chore/update-dependencies` |

### 4. 本地开发

```bash
# 创建 Conda 环境（如果尚未创建）
conda create -n braindance python=3.10
conda activate braindance

# 安装开发依赖
cd ai_engine/3dgs
pip install -r requirements.txt
pip install pytest pytest-cov black flake8 mypy

# 设置 pre-commit 钩子
pre-commit install
```

### 5. 开发流程

```bash
# 1. 编写代码
#    - 遵循代码规范
#    - 添加必要的注释
#    - 编写测试用例

# 2. 运行测试
cd ai_engine/3dgs
python -m pytest tests/ -v

# 3. 代码检查
black .              # 格式化
flake8 .             # 代码风格
mypy src/            # 类型检查

# 4. 提交代码
git add .
git commit -m "feat: 添加语义搜索功能"
git push origin feat/your-feature-name
```

## 📝 代码规范

### Python 代码规范

BrainDance 使用以下工具维护代码质量：

| 工具 | 用途 | 配置 |
|------|------|------|
| **black** | 代码格式化 | `pyproject.toml` |
| **flake8** | 代码风格检查 | `.flake8` |
| **mypy** | 类型检查 | `mypy.ini` |
| **isort** | import 排序 | `pyproject.toml` |

#### 格式化命令

```bash
# 安装工具
pip install black flake8 mypy isort

# 格式化代码
black .

# 检查代码风格
flake8 .

# 类型检查
mypy src/

# 排序 import
isort .
```

#### 代码风格要点

```python
# ✅ 好的例子
def calculate_similarity(
    embedding1: List[float],
    embedding2: List[float],
    method: str = "cosine"
) -> float:
    """
    计算两个向量之间的相似度。

    Args:
        embedding1: 第一个向量
        embedding2: 第二个向量
        method: 相似度计算方法

    Returns:
        相似度分数 (0-1)
    """
    if len(embedding1) != len(embedding2):
        raise ValueError("向量长度必须相同")
    
    # 实现逻辑
    ...


# ❌ 避免的例子
def calc(emb1,emb2,method="cosine"): # 无类型注解、格式混乱
    # 无文档字符串
    if len(emb1)!=len(emb2):
        raise Exception("error")
```

#### 类型注解要求

```python
# ✅ 好的类型注解
from typing import List, Dict, Optional, Union

def process_video(
    video_path: str,
    output_dir: Optional[str] = None,
    options: Dict[str, Union[int, str]] = None
) -> bool:
    """处理视频文件"""
    pass

# ❌ 避免的类型注解
def process_video(video_path, output_dir=None, options=None):  # 无类型
    pass
```

### Git 提交规范

#### 提交信息格式

```
<类型>(<范围>): <描述>

[可选的正文]

[可选的脚注]
```

#### 提交类型

| 类型 | 说明 | 语义版本影响 |
|------|------|--------------|
| `feat` | 新功能 | minor |
| `fix` | Bug 修复 | patch |
| `docs` | 文档更新 | - |
| `style` | 代码格式（不影响功能） | - |
| `refactor` | 重构（既不修复 Bug 也不添加功能） | - |
| `perf` | 性能优化 | patch |
| `test` | 添加/修改测试 | - |
| `chore` | 构建过程或辅助工具的变动 | - |

#### 提交示例

```bash
# ✅ 好的提交
git commit -m "feat(worker): 添加任务优先级支持

- 实现基于优先级的任务调度
- 添加 priority 字段到任务表
- 更新 Worker 抢占逻辑

Closes #123"

# ❌ 避免的提交
git commit -m "update"  # 描述不清
git commit -m "fix bug"  # 过于笼统
git commit -m "wip"      # 不明确的临时提交
```

#### 提交范围

| 范围 | 说明 |
|------|------|
| `core` | 核心流水线代码 |
| `worker` | Worker 相关 |
| `modules` | 功能模块 |
| `utils` | 工具函数 |
| `api` | API 接口 |
| `db` | 数据库相关 |
| `docs` | 文档相关 |

## 🔀 Pull Request 流程

### 1. 创建 Pull Request

1. 访问您的 Fork 仓库页面
2. 点击 **New Pull Request** 按钮
3. 选择源分支和目标分支
4. 填写 PR 模板

#### PR 模板

```markdown
## 描述
<!-- 简要描述您的更改 -->

## 更改类型
- [ ] 🐛 Bug 修复
- [ ] ✨ 新功能
- [ ] 📝 文档
- [ ] 🎨 代码格式
- [ ] ♻️ 重构
- [ ] ⚡ 性能优化
- [ ] ✅ 测试

## 测试
- [ ] 我已添加测试用例
- [ ] 所有测试通过
- [ ] 测试覆盖率未下降

## 检查清单
- [ ] 代码遵循项目规范
- [ ] 代码经过格式化检查
- [ ] 类型检查通过
- [ ] 文档已更新（如需要）

## 相关 Issue
<!-- 关联的 Issue 编号，如：Closes #123 -->
```

### 2. PR 描述示例

```markdown
## 描述

为 AI Worker 添加任务优先级支持，实现基于优先级的任务调度。

### 主要更改

1. 在 `processing_tasks` 表中添加 `priority` 字段
2. 修改 Worker 抢占逻辑，支持优先级排序
3. 添加相关单元测试

### 测试结果

```
pytest tests/core/test_worker.py -v
✓ test_worker_initialization
✓ test_task_polling_with_priority
✓ test_priority_sorting
```

### 相关 Issue

此 PR 解决 #123：需要支持任务优先级
```

### 3. 保持 PR 精简

**推荐**：

- PR 包含 1 个逻辑上相关的更改
- PR 行数 < 500 行
- PR 文件数 < 10 个

**避免**：

- 在一个 PR 中混合多个不相关的更改
- 过大的 PR（难以审查）
- 包含不必要的文件（如生成的二进制文件）

### 4. PR 生命周期

```
[Draft PR] → [Ready for Review] → [Changes Requested] → [Approved] → [Merged]
     ↑                                              ↓
     └──────────────────────────────────────────────────┘
                (根据反馈修改代码)
```

## 👀 代码审查

### 作为贡献者

#### 期望行为

1. **响应审查意见**：及时回复审查者的评论
2. **解释决策**：如果不同意审查意见，解释您的理由
3. **简化更改**：如果审查者要求简化，尝试找到更好的实现方式
4. **保持专业**：即使有分歧，也要保持礼貌和专业

#### 处理审查意见

```markdown
<!-- 示例：回复审查意见 -->

**审查者**：这个函数太长了，建议拆分成多个函数。

**您**：
> 我同意您的建议。我将其拆分为三个函数：
> - `validate_input()`: 输入验证
> - `process_data()`: 数据处理  
> - `format_output()`: 输出格式化
> 
> 新实现更清晰，测试也更容易。

<!-- 示例：解释决策 -->

**审查者**：为什么使用列表而不是生成器？

**您**：
> 生成器虽然节省内存，但这里需要：
> 1. 多次遍历数据
> 2. 返回固定大小的结果列表
> 
> 在这个场景下，列表更合适。
```

### 作为审查者

#### 审查原则

1. **友好专业**：使用鼓励性语言，避免傲慢或批评
2. **聚焦重点**：关注关键问题，容忍风格差异
3. **提供建议**：不仅指出问题，还要提供解决方案
4. **及时审查**：尽快完成审查，不阻塞流程

#### 审查清单

```markdown
## 代码审查清单

### 功能性
- [ ] 代码是否实现了需求？
- [ ] 是否处理了边界情况？
- [ ] 错误处理是否完善？

### 可读性
- [ ] 代码是否清晰易懂？
- [ ] 命名是否直观？
- [ ] 是否有必要的注释？

### 性能
- [ ] 是否有明显的性能问题？
- [ ] 是否正确使用了数据结构？
- [ ] 是否避免了不必要的重复计算？

### 测试
- [ ] 是否添加了测试？
- [ ] 测试是否覆盖了主要场景？
- [ ] 测试是否通过？

### 安全
- [ ] 是否存在安全漏洞？
- [ ] 输入验证是否充分？
- [ ] 是否避免了注入风险？
```

## ❓ 常见问题

### Q1: 如何找到适合新手的 Issue？

A: 寻找带有 `good first issue` 标签的 Issue。这些 Issue 通常：
- 范围明确，便于理解
- 改动较小，易于完成
- 有详细的说明和指导

### Q2: PR 被拒绝了怎么办？

A: 不要气馁！PR 被拒绝是正常的：
1. 仔细阅读审查意见
2. 理解拒绝的原因
3. 根据反馈修改代码
4. 重新提交或继续讨论

### Q3: 如何处理大型 PR？

A: 如果您的更改较大：
1. 将其拆分为多个小 PR
2. 每个 PR 聚焦于一个功能
3. 确保每个 PR 都是独立可合并的

### Q4: 如何同步上游仓库？

```bash
# 获取上游最新代码
git fetch upstream

# 合并到当前分支
git checkout dev
git merge upstream/dev

# 推送到您的 Fork
git push origin dev
```

### Q5: 可以直接提交到 main 分支吗？

A: **不可以**。所有更改必须通过 Pull Request 流程：
1. 从功能分支创建 PR
2. 通过代码审查
3. 合并到 dev 或 main 分支
